# Архитектурная Доктрина VectorWorkspace (Rules for Agents)

Эта доктрина определяет правила работы с проектом VectorWorkspace (Tauri + React + TypeScript) и обязательна к исполнению для всех агентов. 
Мы категорически отвергаем Feature-Sliced Design (FSD), Redux Toolkit и прочую корпоративную бюрократию в пользу прагматичной, плоской и быстрой архитектуры.

## 1. Базовая Идеология
* **Никакого Over-engineering.** Если задачу можно решить через локальный state (`useState`) или React Context, использование глобальных менеджеров состояния ЗАПРЕЩЕНО.
* **Никакого излишнего дробления доменной логики.** Чистые математические генераторы и бизнес-правила (`word-generator.ts`, `editorModel.ts`) живут в единых файлах. Не разбивайте их на 10 мелких утилит без приказа.
* **Tauri-First.** Для работы с файловой системой всегда используйте нативные плагины (`@tauri-apps/plugin-fs`, `@tauri-apps/plugin-dialog`). Встраивать браузерные фоллбэки (типа `file-saver`) ЗАПРЕЩЕНО.

## 2. Структура Директорий (Pragmatic Feature Folders)
Код организован по доменным зонам (features). Папка `panels/` упразднена в пользу `domains/`.

\`\`\`text
src/
├── app/                  # Конфигурация приложения (App.tsx, main.tsx)
├── services/             # Связь с Tauri (api.ts)
├── shared/               # Переиспользуемый базис
│   ├── ui/               # Глупые UI-компоненты (Button, Modal, Stat, Section)
│   └── lib/              # Утилиты
└── domains/              # Доменные блоки
    ├── settings/         
    ├── tup/              
    └── ktp/
\`\`\`

## 3. Разделение Логики и UI (Правило Хуков)
Файлы `.tsx` не должны превышать 200-250 строк.
Если компонент растет, применяйте следующий алгоритм расчленения:

1. **Извлечение Логики:** Вся логика работы с данными (загрузка, фильтрация, обработка кнопок, стейты FTS-поиска) **выносится в кастомный хук** внутри домена (например, `useTupList.ts` или `useKtpEditorState.ts`). Хук должен возвращать только готовые данные и коллбэки.
2. **Изоляция UI:** Сам `.tsx` файл должен стать "глупым" потребителем хука.
3. **Разбиение на блоки:** Если UI все еще огромен, разбейте его на подкомпоненты (карточки, модалки, секции) и сложите их в папку `ui/` внутри домена (например, `domains/tup/ui/TupParagraph1.tsx`).
4. **Оркестрация:** Файл-оркестратор (например, `domains/tup/ui/TupList.tsx`) должен только вызывать хук и передавать данные в подкомпоненты.

## 4. Именование (Naming Conventions)
* **Папки доменов:** `camelCase` (например, `tup/`, `settings/`).
* **Папка подкомпонентов:** Всегда называется `ui/`. 
* **Файлы компонентов:** `PascalCase.tsx` (например, `TupDetail.tsx`). Никаких бессмысленных `index.tsx` внутри доменов. Имя файла обязано точно совпадать с именем компонента.
* **Файлы логики/хуков:** `camelCase.ts` (например, `useTupDetail.ts`).

## 5. Стилизация
* Проект использует **Tailwind CSS v4** (`@tailwindcss/vite`).
* Кастомные CSS-классы в `styles.css` допускаются только для глобальных макетов или если Tailwind не справляется с задачей. 
* Не пишите inline styles (`style={{...}}`), переводите их в классы Tailwind, где это возможно.

## 6. Как принимать решения
Если пользователь просит добавить новую фичу:
1. Найди подходящий домен в `src/domains/` или создай новый.
2. Напиши логику в `useFeatureName.ts`.
3. Создай UI-компоненты в `domains/featureName/ui/`.
4. Собери всё вместе и подключи к `MainLayout.tsx` (если это новая страница) или внутрь существующего оркестратора.
