## Часть A. Правки редактора (13 замечаний)

### A1. Проверить ссылки на законы РК / приложение ТУП
- **Задача.** При создании КТП 10 класса по алгебре подтянулась неверная ссылка на приложение, по которому создан ТУП. Ссылки на норматив должны быть корректными для каждой пары «предмет × класс».
- **Метод решения.**
  1. Расширить модель ТУП (`StoredTup` в `circulumPlan/model/types.tsx`) полем `sourceRef` (приказ/приложение, кем и когда утверждён).
  2. При загрузке/парсинге ТУП заполнять `sourceRef` из эталонного реестра (карта «предмет × класс → приказ/приложение», источник — adilet/приказы МП РК).
  3. При генерации КТП пробрасывать `sourceRef` в `SavedKtp`, выводить в настройках КТП и подставлять в пояснительную записку/титульный лист.
  4. Если для пары нет эталона — не подставлять «универсальную» ссылку, а помечать «источник не определён».
- **Что решает.** Юридическая корректность документов; убирает риск сдачи КТП с чужим приложением.
- **Метрики качества.**
  - Для алгебры 10 класса подставляется эталонное приложение (совпадает с приказом), не «общее» значение.
  - Карта «предмет × класс → приказ» покрыта юнит-тестом.
  - Отсутствие эталона → статус «источник не определён», а не подмена.

### A2. Запретить перенос уроков между разделами
- **Задача.** Drag-and-drop (`reorderPlan`) сейчас позволяет перетащить урок в другой раздел (и другую четверть).
- **Метод решения.**
  1. В `reorderPlan` (или на уровне `handleDragEnd` в `KTPEditor`) сравнивать `sectionName` (и номер четверти) `active` и `over` уроков.
  2. Если разделы/четверти разные — операцию не выполнять и показать подсказку/подсветку.
  3. Ограничить `SortableContext` контекстом раздела, чтобы сенсоры не реагировали на чужой раздел.
- **Что решает.** Целостность методической структуры: урок не «уезжает» в чужой раздел и не ломает логику СОР/СОЧ.
- **Метрики качества.**
  - Юнит-тест `reorderPlan`: перенос внутри раздела выполняется, между разделами/четвертями — план не меняется.
  - Ручная проверка: перетаскивание в чужой раздел даёт понятную подсказку.

### A3. Не создавать плашку раздела после СОР
- **Задача.** При перемещении урока под СОР появляется плашка/разделитель с названием раздела (`isSectionEnd`/`isNewSection` в `KTPTableRow`).
- **Метод решения.**
  1. СОР-урок имеет тот же `sectionName`, что и раздел — исключить СОР из логики `isNewSection`/`isSectionEnd`.
  2. Разделитель «Добавить СОР» и плашка конца раздела не должны рисоваться после/внутри СОР.
- **Что решает.** Чистая визуальная структура таблицы без лишних плашек.
- **Метрики качества.**
  - После СОР (и после урока, перемещённого под СОР) нет плашки раздела.
  - Визуальный чек-лист на реальном плане.

### A4. Урок СОР дублирует тему и цель последнего обычного урока
- **Задача.** При создании СОР в разделе тема/цель СОР должны повторять тему/цель последнего стандартного урока раздела.
- **Метод решения.**
  1. В `addSor` (`slice.ts`) оставить `objectives = sectionLastLesson.objectives`, тему СОР сделать равной `sectionLastLesson.lessonTopic`.
  2. Убрать из темы декоративный текст «СОР №N по разделу "…"».
- **Что решает.** Методическая преемственность: СОР за раздел оценивает материал последнего урока.
- **Метрики качества.**
  - Юнит-тест `addSor`: `topic` и `objectives` СОР равны последнему стандартному уроку раздела; в теме нет подстроки «СОР №».

### A5. Видимое обрамление таблицы по краям
- **Задача.** У таблицы не видно внешней рамки по краям (задана только `borderRight` в `StyledTableCell`).
- **Метод решения.**
  1. Задать `border` на `TableContainer`/`Table` и добавить левую/верхнюю/нижнюю границы ячеек.
  2. Сохранить `stickyHeader` и не сломать объединённые строки (quarter-header, плашки).
- **Что решает.** Таблица читается как цельный бланк, пригодный к печати.
- **Метрики качества.**
  - Визуально видны все 4 стороны рамки (чек-лист/скриншот).
  - Нет «рваных» границ в объединённых ячейках.

### A6. Четверть — отдельным цветом, без hover, с указанием часов
- **Задача.** Строку-заголовок четверти (`QUARTER_HEADER`) явно выделить цветом, убрать реакцию на наведение и показывать запланированные часы четверти.
- **Метод решения.**
  1. Задать отдельный фоновый цвет для `QUARTER_HEADER`, отключить hover-эффекты на этой строке.
  2. В заголовке выводить часы четверти из `quarterWorkHours` (уже есть поле «Часы» — сделать его явным и читаемым).
- **Что решает.** Ориентация в плане: сразу видно границы четвертей и их объём.
- **Метрики качества.**
  - На строке четверти нет hover-реакции; цвет отличен от остальных типов.
  - Часы четверти отображаются и редактируются.

### A7. Валидация количества часов (норма vs факт) в реальном времени
- **Задача.** Система должна постоянно сверять норму часов предмета с фактическим планом и показывать ошибки в реальном времени.
- **Логика.** Дни проведения (пн/ср/пт) → 3 урока/нед; 1, 2, 4 четверти — 8 недель, 3-я — 10 недель → `3·8·3 + 3·10 = 102`. Далее по каждой четверти: «должно быть / запланировано / фактически», с учётом объединений (совпадающие даты).
- **Метод решения.**
  1. Выделить чистый сервис `hoursValidation` (переиспользуя логику `possibleLessons` и `autofillDates`): расчёт учебных дней по четвертям, расчёт «должно быть», подсчёт фактических уроков и объединений.
  2. Считать фактическое как: количество уроков с датами + объединения (одинаковые даты → 1 фактическое занятие).
  3. Вывести панель сверху редактора (`memo`/селектор, пересчёт при любом изменении `plan`/`quarterWorkHours`/дней).
  4. Пример вывода: «1 четв.: должно 24, запланировано 24, фактически 23 (1 объединение — 25 окт.); 2 четв.: должно 24, запланировано 20, фактически 20 — не хватает 4 уроков, 1 объединение (16 дек.)».
- **Что решает.** Соответствие нормативной нагрузке; мгновенное выявление нехватки/избытка часов и объединений.
- **Метрики качества.**
  - Контрольный расчёт `3·8·3 + 3·10 = 102` сходится.
  - Пример из замечания воспроизводится в выводе (1-я и 2-я четверти).
  - Пересчёт происходит без перезагрузки; юнит-тесты на расчёт дней, «должно/запланировано/фактически», объединений.

### A8. Уроки повторения: тема и цель в одну строку
- **Задача.** У `REPETITION` убрать отдельную колонку целей: тема и цель — одна строка. Вместо слова «Повторение» подставлять название раздела. Количество тем = количеству разделов, но не меньше двух (если раздел один — дублировать).
- **Метод решения.**
  1. В генераторе повторений (`lib.ts`) формировать уроки повторения по названиям разделов (`max(2, sections.length)`), дублируя при нехватке.
  2. В рендере `REPETITION` объединить тему и цель в одну ячейку (colspan), без отдельной колонки целей.
- **Что решает.** Повторение привязывается к реальным разделам, таблица компактнее.
- **Метрики качества.**
  - Юнит-тест: при 3 разделах — 3 темы повторения с названиями разделов; при 1 разделе — 2 темы (дубль).
  - Рендер повторения в одну строку без колонки целей.

### A9. СОЧ: тема и цель в одну строку
- **Задача.** У `SOCH` тема и цель — одна строка; вместо «СОЧ» писать «Суммативное оценивание за 1/2/3/4 четверть».
- **Метод решения.**
  1. В генераторе (`lib.ts`) для СОЧ проставлять тему по номеру четверти: «Суммативное оценивание за N четверть».
  2. Рендер СОЧ в одну ячейку (тема+цель), без отдельной колонки целей.
- **Что решает.** Корректное наименование контрольной работы, компактный вид.
- **Метрики качества.**
  - Текст корректный для четвертей 1–4 (тест).
  - Рендер в одну строку.

### A10. Между СОР и СОЧ — промежуточный урок
- **Задача.** Между СОР и СОЧ должен быть урок (не «повторение») — дубликат последней темы с последней целью.
- **Метод решения.**
  1. При генерации/валидации вставлять перед СОЧ урок-дубликат последнего стандартного урока (та же тема/цель), тип `STANDARD`.
  2. Соблюсти инвариант FR-2.2: `Index(Soch) - Index(Last_Sor) = 2`.
- **Что решает.** Методическая дистанция СОР → СОЧ без потери учебного часа.
- **Метрики качества.**
  - Инвариант дистанции выполняется после генерации (тест в `invariants.test.ts`).
  - Вставленный урок — копия темы/цели последнего стандартного урока.

### A11. Объединение целей в один урок
- **Задача.** Дать возможность объединить две цели разных уроков одной темы в один урок (простая цель + простая цель).
- **Метод решения.**
  1. Доработать UX поверх `mergeObjectives` (перетаскивание цели) и кнопки «Объединить со следующим уроком»: явное действие «объединить цели со следующим уроком этой темы».
  2. При объединении переносить цели в целевой урок, удалять исходный, пересчитывать нумерацию (`renumberPlan`).
- **Что решает.** Гибкое планирование при «лёгких» темах; не раздувает КТП лишними уроками.
- **Метрики качества.**
  - После объединения два урока одной темы → один урок с двумя целями; цели не теряются.
  - Нумерация корректна (тест).

### A12. Импорт нормативных часов («Норма часов»)
- **Задача.** Поле «Норма часов» в настройках КТП, куда вводится норма по предмету (например, 102 по алгебре); система постоянно сверяет план vs норма (см. A7).
- **Метод решения.**
  1. Добавить поле `normHours` в состояние редактора и в настройки (рядом с «Общее количество часов»).
  2. Подключить к валидатору часов из A7: сверка нормы по четвертям и общая.
  3. Сохранять `normHours` в `SavedKtp`/Supabase.
- **Что решает.** Явный источник нормы для валидации часов, без ручного пересчёта.
- **Метрики качества.**
  - Ввод 102 → сверка по четвертям работает и показывает ошибки в реальном времени.
  - Значение нормы сохраняется и восстанавливается.

### A13. 1–4 классы: нет СОР и СОЧ
- **Задача.** По новому закону в 1–4 классах СОР и СОЧ отменены. Перед генерацией — пункт «Добавить СОР и СОЧ» и плашка об отмене для 1–4 классов.
- **Метод решения.**
  1. На шаге создания КТП из ТУП — переключатель/чекбокс «Добавить СОР и СОЧ».
  2. Если класс 1–4 — показывать плашку «СОР и СОЧ отменены для 1–4 классов», СОР/СОЧ не добавлять.
  3. Для 5+ классов сохранить текущее поведение (добавлять по умолчанию/по флагу).
- **Что решает.** Соответствие новому закону; не создаёт несуществующие контрольные.
- **Метрики качества.**
  - Для grade 1–4 СОР/СОЧ не генерируются, плашка отображается.
  - Для grade 5+ поведение без изменений (тест).

## Часть B. Избранные фичи (в план)

### B1. Undo / Redo + история изменений
- **Задача.** Откат и повтор любого действия редактора (перенос, объединение, удаление, СОР/СОЧ) с лентой действий.
- **Метод решения.**
  1. Хранить историю как стеки `past`/`present`/`future` снапшотов `plan` (или минимальных патчей) в состоянии редактора.
  2. Подключить через middleware/обёртку так, чтобы каждый мутирующий reducer фиксировал предыдущее состояние.
  3. Горячие клавиши `Ctrl+Z`/`Ctrl+Y`, панель истории (список шагов с подписью действия и таймстемпом).
  4. Кап истории (например, 100 шагов) для ограничения памяти.
- **Что решает.** Защита от случайных правок, быстрое восстановление.
- **Метрики качества.**
  - Любое из действий (перенос/объединение/удаление/СОР/СОЧ) обратимо и повторимо.
  - `Ctrl+Z`/`Ctrl+Y` работают; лента показывает шаги.
  - Юнит-тест последовательности действий; снапшот плана из 300 уроков фиксируется < 50 мс.

### B2. Библиотека шаблонов КТП (клонирование на параллельный класс)
- **Задача.** Сохранить план как шаблон и клонировать на параллельный класс (7а → 7б) одной кнопкой.
- **Метод решения.**
  1. Хранилище шаблонов (localStorage сейчас, затем таблица Supabase `ktp_templates`).
  2. Действия: «Сохранить как шаблон», «Создать из шаблона» с указанием класса.
  3. При клонировании: очищать даты и класс-специфичные поля, сбрасывать нумерацию, сохранять структуру (разделы/темы/цели/типы уроков).
- **Что решает.** Экономия времени на параллельных классах, единообразие планов.
- **Метрики качества.**
  - Клон создаёт КТП с тем же составом уроков, пустыми датами и новым классом.
  - Шаблон создаётся/удаляется/переиспользуется (тест).

### B3. Глобальное резервное копирование и восстановление
- **Задача.** Выгрузка всего, что касается пользователя (КТП, ТУП, КСП, СОР/СОЧ, настройки, календарь), в один файл и импорт на другом устройстве.
- **Метод решения.**
  1. Единый пакет-экспорт JSON с `schemaVersion` и манифестом секций.
  2. Расширяемый реестр сериализаторов: сейчас КТП + ТУП + настройки + календарь; далее добавить КСП, СОР/СОЧ без изменения формата.
  3. Импортёр с валидацией схемы, детектом конфликтов `id` и merge-стратегией (перезапись/пропуск/создать копию).
  4. Кнопки «Экспорт данных» / «Импорт данных» в настройках.
- **Что решает.** Перенос между устройствами, страховка от потери данных.
- **Метрики качества.**
  - Round-trip (экспорт → импорт) восстанавливает все данные без потерь.
  - Битые/неверные файлы отклоняются с понятной ошибкой.
  - Конфликтные `id` обрабатываются; формат версионирован (тест).

### B4. Прогресс-бар готовности
- **Задача.** Наглядная шкала по четвертям: сколько уроков заполнено, сколько осталось, % готовности.
- **Метод решения.**
  1. Селектор готовности: урок «заполнен», если заданы тема, цели и дата.
  2. Агрегация по четвертям и по плану в целом.
  3. Визуализация прогресс-баров в шапке редактора; клик по четверти → список незаполненных уроков.
- **Что решает.** Видимость полноты плана, быстрое нахождение пробелов.
- **Метрики качества.**
  - % готовности считается корректно (юнит-тест селектора).
  - Клик по четверти показывает незаполненные уроки.

## Часть C. На потом (рассмотреть)

### C1. Экспорт в PDF + отдельные редакторы титульного листа и пояснительной записки
- **Задача.** Отдельные полноценные редакторы титульного листа и пояснительной записки, связанные с КТП; PDF/печатная форма с грифами «Рассмотрено/Согласовано/Утверждаю».
- **Метод решения.**
  1. Вынести титульный лист и ПЗ в самостоятельные сущности с обратной связью `ktp_id` (двусторонняя связь, без дублирования данных).
  2. Развить существующие `TitlePageWidget`/`ExplanatoryNoteWidget` в полноценные редакторы.
  3. Материализация PDF (грифы, подписи директора/завуча/МО, колонтитулы), экспорт из КТП и обратно.
- **Что решает.** Полный пакет документов учителя из одного плана.
