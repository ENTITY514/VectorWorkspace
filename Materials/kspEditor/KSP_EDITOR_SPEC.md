## 1. Что уже есть в проекте

Прежде чем проектировать, важно понимать точку старта — она лучше, чем кажется.

| Компонент | Состояние | Комментарий |
|---|---|---|
| Таблица `ksp_documents` | ✔ Есть в миграции `0001` | `ktp_lesson_id`, `teacher_id`, `is_approved`, `content` (JSON) |
| Типы `Ksp`, `KspStages` | ⚠ Есть в `types.ts:142-164`, **не используются нигде** | Содержат поле `resources`, которого нет в вашей спецификации |
| Rust-команды КСП | ✘ Отсутствуют полностью | КСП — greenfield: ни одной команды, ни репозитория, ни UI |
| КТП (план, четверти, уроки, цели) | ✔ Полностью реализовано | `ktp_lessons` + `ktp_lesson_objectives` → FK на `learning_objectives` |
| ТУП с целями обучения | ✔ Реализовано, есть FTS5 | Источник целей и «программы Адилет» |
| Учебники | ◐ Схема есть, данных нет | `textbooks`, `textbook_paragraphs`, `textbook_tasks` (`raw_latex_condition`, `difficulty` LevelA/B/C), `textbook_tasks_fts` |
| СОР/СОЧ и дескрипторы | ◐ Схема есть, кода нет | `sor_specifications.total_score`, `sor_descriptors.points` |
| MCP-сервер | ✘ Только архитектурный документ | `docs/08-mcp-core.md` описывает Staging Quarantine, Tool Registry, Context Reducer |
| Расписание | ✔ Реализовано | `schedule_slots` — источник факта «когда урок стоит» |

**Вывод.** Схема данных под КСП заложена грамотно, но код полностью отсутствует. Это удача: можно спроектировать правильно с нуля, не ломая работающее.

## 2. Конфликты с существующей спецификацией

### ⚠️ К1. Пять столбцов против шести — исчезли «Ресурсы»

Ваша спецификация: **Этап · Действия учителя · Действия ученика · Оценивание** (+ время = 5 столбцов).
`docs/05-ksp.md` и типы в `types.ts`: те же плюс **`resources`**.

Форма Приказа МОН РК № 130 содержит графу ресурсов (учебник, страница, раздаточный материал, ссылка). Завучи проверяют её наличие.

**Предложение:** оставить 5 столбцов **в таблице**, а ресурсы сделать вложенной сущностью внутри «Действий учителя» — структурированным списком ссылок (учебник + номер задания, файл, ссылка). Это одновременно:
- сохраняет вашу компактную таблицу;
- даёт машиночитаемую связь с `textbook_tasks` (нужно для MCP и RAG);
- при экспорте в Word ресурсы автоматически разворачиваются в отдельную графу по форме № 130.

**Решение требуется от вас:** принять или отвергнуть.

### ⚠️ К2. Терминология «воспитательная цель по программе Адилет»

В `docs/05-ksp.md` это `traditional_values` (национальные и общечеловеческие ценности). В вашей формулировке — «воспитательная цель по программе Адилет». Полагаю, речь об одном и том же: значения из нормативного акта на adilet.zan.kz.

**Предложение:** поле `values_component` с двумя частями — `value_ids[]` (ссылки на справочник ценностей из нормативного документа) + `text` (формулировка учителя). Справочник ценностей заводится один раз, а не набивается текстом в каждом КСП.

### ⚠️ К3. Старую спецификацию нужно либо обновить, либо отменить

`docs/05-ksp.md` останется источником противоречий, если его не привести в соответствие. После утверждения этого документа он должен быть заменён ссылкой сюда.

## 3. 20 пробелов исходной спецификации и решения

Это ядро документа: то, чего в спецификации нет, но без чего редактор не заработает.

### 🔴 G1. Один урок КТП ↔ несколько классов

**Проблема.** `ksp_documents.ktp_lesson_id` объявлен `UNIQUE`: один урок КТП = один КСП. Но `ktp_plans` привязан к `subject_id + grade + academic_year` — **класса там нет**. Учитель ведёт «Алгебра, 7 класс» в 7А, 7Б, 7В. По одной теме нужны три КСП с разными датами и, возможно, разной дифференциацией.

Ваша шапка содержит «класс» — значит, КСП поклассный. Текущая схема этого не допускает.

**Решение.**
```sql
-- Ключ становится составным
ALTER TABLE ksp_documents ADD COLUMN class_id TEXT REFERENCES classes(id);
DROP INDEX ...; -- снять UNIQUE(ktp_lesson_id)
CREATE UNIQUE INDEX uq_ksp_lesson_class ON ksp_documents(ktp_lesson_id, class_id);
```
➕ Плюс функция «Клонировать КСП в другой класс» — 80 % содержания совпадает, меняются дата, дифференциация и домашнее задание.

### 🔴 G2. Формативное оценивание не имеет баллов

**Проблема.** В спецификации сказано: «всего 10 баллов» для дескрипторов. Но по критериальному оцениванию РК **формативное оценивание безоценочное** — оно даёт обратную связь, а не баллы. Баллы существуют только в СОР и СОЧ. Если редактор потребует 10 баллов на обычном уроке, учителя будут заполнять поле формально, а завуч отметит методическую ошибку.

**Решение.** Разделить два режима оценивания на уровне модели:

| Режим | Где применяется | Что содержит | Валидация |
|---|---|---|---|
| `formative` | Теория, практика, ФО, рефлексия | Критерии успеха + дескрипторы **без баллов** («умеет», «затрудняется») | Дескриптор привязан к цели обучения |
| `summative` | СОР, СОЧ | Задания + дескрипторы **с баллами** | Σ баллов = `total_score` спецификации СОР/СОЧ |

Правило «10 баллов» становится значением по умолчанию для `summative`, настраиваемым в конфиге — как вы и предложили, но с явным указанием, что на обычном уроке блок баллов скрыт.

### ➕ G3. Дифференциация как структура, а не проза

**Проблема.** В спецификации дифференциация — часть текста «Действий учителя». Тогда её нельзя ни проверить, ни связать с заданиями учебника, а `textbook_tasks.difficulty` (LevelA/LevelB/LevelC) уже существует в схеме и остаётся неиспользованным.

**Решение.** Внутри этапа — опциональный блок:
```json
"differentiation": {
  "level_a": { "description": "...", "task_ids": ["..."] },
  "level_b": { "description": "...", "task_ids": ["..."] },
  "level_c": { "description": "...", "task_ids": ["..."] }
}
```
Задания подтягиваются из учебника по уровню сложности; MCP получает инструмент «подбери задания уровня B к цели 7.2.1.4».

### 🔴 G4. Нет сущности «фактическое проведение урока»

**Проблема.** Вы просите MCP-функцию «саммари предыдущего урока: что сделали, какие задания решали, какое ДЗ, что проверить». Но КСП — это **план**. Пока нет записи о факте, саммари будет пересказом плана, а не отчётом о том, что реально произошло. Урок сорвался, класс не успел половину, задали другое — план об этом не знает.

**Решение.** ➕ Новая таблица `ksp_lesson_runs`:
```sql
CREATE TABLE ksp_lesson_runs (
    id TEXT PRIMARY KEY,
    ksp_id TEXT NOT NULL REFERENCES ksp_documents(id) ON DELETE CASCADE,
    actual_date TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('planned','conducted','cancelled','postponed')),
    completed_stage_ids TEXT NOT NULL DEFAULT '[]',  -- что успели
    actual_homework TEXT,                            -- что реально задали
    carry_over TEXT,                                 -- что перенесено на следующий урок
    teacher_note TEXT,
    created_at TEXT NOT NULL
);
```
Саммари строится из `ksp_lesson_runs`, а при его отсутствии честно помечается как «план, факт не зафиксирован».

### ➕ G5. Домашнее задание — сущность, а не текст этапа

**Проблема.** «Домашнее задание» указано как тип этапа. Но ДЗ живёт дольше урока: его нужно проверить на следующем, оно связывает «актуализацию» урока N+1 с уроком N.

**Решение.** Отдельный блок с полями: `tasks[]` (ссылки на `textbook_tasks` или свободный текст), `due_lesson_id`, `check_method`, `is_differentiated`. MCP-функция «что проверить на следующем уроке» становится тривиальным запросом, а не пересказом.

### ➕ G6. Актуализация без явной связи с предыдущим уроком

**Проблема.** Вы верно определили актуализацию как «проверить прошлое либо подготовить новое». Но связь с конкретным предыдущим уроком нигде не хранится.

**Решение.** У этапа типа `actualization` — поля `references_lesson_id` и `references_homework: bool`. Тогда редактор сам предложит: «на прошлом уроке задано № 145–147, добавить проверку?».

### ⚠️ G7. Политика расхождений с КТП

**Проблема.** Вы требуете «полную сверку по разделу, теме, цели и дате». Но даты в реальности плывут: карантин, праздники, замена, болезнь учителя. Жёсткая блокировка сделает редактор неработоспособным уже во второй четверти.

**Решение.** Разделить поля по строгости:

| Поле | Политика | Обоснование |
|---|---|---|
| Раздел, тема | 🔒 **Только из КТП**, редактирование запрещено | Наследуется по FK, ручной ввод исключён |
| Цели обучения | 🔒 Только из `ktp_lesson_objectives` | Выбор из списка целей урока, не текст |
| Дата | ⚠️ **Предупреждение при расхождении**, не блокировка | Дрейф фиксируется в `ksp_lesson_runs.actual_date`; накопленный сдвиг показывается в КТП как «отставание N уроков» |
| Класс, учитель | Из расписания | См. G8 |

Изменение темы или цели возможно **только через редактирование КТП** — ровно как вы и написали. Редактор КСП предоставляет кнопку «Открыть урок в КТП».

### ➕ G8. Шапка должна заполняться автоматически

**Проблема.** Дата, класс, учитель перечислены как поля шапки. Заполнять их вручную — источник ошибок и расхождений с расписанием.

**Решение.** Шапка собирается из связей: `ktp_lessons` (раздел, тема, цели, плановая дата) + `schedule_slots` (класс, учитель, кабинет, номер урока в дне) + `teacher_profiles` (ФИО). Учитель ничего не вводит — только проверяет.

### ➕ G9. Статусы и жизненный цикл КСП

**Проблема.** В схеме есть только `is_approved INTEGER`. Этого мало: непонятно, черновик ли это, отправлен ли завучу, проведён ли урок.

**Решение.** `status`: `draft` → `ready` → `approved` → `conducted` → `archived`. Правки после `approved` создают новую версию (см. G10), а не переписывают документ.

### ➕ G10. Версионирование и история

**Проблема.** Не предусмотрено. При этом MCP-агент будет массово править содержимое — без истории откатить неудачную правку невозможно.

**Решение.** `ksp_revisions` (снимок `content` + автор + причина + timestamp). Обязательно для доверия к AI-правкам: любое изменение агента отменяется одной кнопкой.

### ➕ G11. Цели урока ≠ цели обучения

**Проблема.** В спецификации только «цель обучения по программе». Но форма № 130 различает **цели обучения** (из ТУП, код вида `7.2.1.4`) и **цели урока** (SMART-декомпозиция: «все учащиеся смогут…, большинство…, некоторые…»).

**Решение.** Два поля: `learning_objectives[]` (FK, только из КТП) и `lesson_goals` со структурой `{ all: "", most: "", some: "" }`. Второе поле хорошо ложится на дифференциацию из G3.

### ➕ G12. Язык КСП

**Проблема.** Школа работает с ТУП на двух языках (`tup_kz.json`, `tup_ru.json`), а язык КСП нигде не задан.

**Решение.** Поле `language` (`kk` / `ru`); шаблоны этапов, экспорт и подсказки MCP локализуются. Для казахских классов формулировки целей подтягиваются из казахской версии ТУП.

### ➕ G13. Экспорт в Word/PDF — не упомянут вообще

**Проблема.** Учителя сдают КСП завучу в бумажном или docx-виде. Без экспорта редактор бесполезен вне приложения. В проекте уже есть `docx` (npm) и генераторы для ТУП — база готова.

**Решение.** Экспорт по форме Приказа № 130: docx, PDF, пакетный экспорт (все КСП за четверть одним файлом).

### ➕ G14. Шаблоны уроков

**Проблема.** Учитель ведёт 20+ уроков в неделю. Собирать каждый КСП с нуля из 7 этапов — нереалистично.

**Решение.** Библиотека шаблонов: «Урок изучения нового», «Урок закрепления», «Урок СОР», «Комбинированный». Шаблон задаёт набор этапов с хронометражем; учитель наполняет содержанием. ➕ Плюс «Создать по образцу прошлого урока».

### ➕ G15. Метрики качества КСП

**Проблема.** Валидация отвечает «да/нет», но не показывает качество.

**Решение.** Панель метрик: покрытие целей обучения этапами, доля практики против теории, доля времени на оценивание, наличие дифференциации, связь с учебником. Не блокирует сохранение — информирует.

### ⚠️ G16. «Можно ли ставить урок» — требует определения

**Проблема.** Формулировка операции валидации в MCP расплывчата.

**Решение.** Определяем как **готовность к проведению** — чек-лист:
1. КСП валиден (все блокирующие правила пройдены);
2. урок присутствует в расписании на эту дату (`schedule_slots`);
3. предыдущий урок проведён либо явно отменён;
4. ДЗ предыдущего урока имеет способ проверки;
5. для СОР/СОЧ — спецификация существует и баллы сходятся;
6. КСП в статусе `ready` или выше.

### ➕ G17. MCP: отсутствуют операции удаления и переупорядочивания

**Проблема.** Перечислены «добавить этап» и «редактировать этап». Нет удаления, перемещения, разделения и слияния этапов, а также пересчёта хронометража.

**Решение.** См. §10 — полный набор из 18 инструментов.

### 🔴 G18. MCP: не описана транзакционность и защита от агента

**Проблема.** В `docs/08-mcp-core.md` спроектирован Staging Quarantine (артефакт в памяти → валидация → визуальный дифф → атомарный коммит), но в вашей спецификации MCP-функции описаны как прямые мутации. Без карантина агент способен испортить документ без возможности отката.

**Решение.** Все мутирующие инструменты MCP работают **только** через staging: возвращают `staged_id` и дифф, а фиксация — отдельным подтверждением пользователя. Плюс `dry_run` у каждого мутирующего инструмента.

### ➕ G19. Приватность: агент не должен видеть персональные данные

**Проблема.** Не оговорено. КСП может содержать имена учеников («Ахмет отвечает у доски»), а запросы уходят к облачному провайдеру.

**Решение.** Обезличивание на границе MCP: ФИО учеников заменяются на `[Ученик 1]`. Правило проверяется тестом.

### ➕ G20. RAG учебника: нет схемы под чанки, эмбеддинги и происхождение

**Проблема.** Существующие `textbook_paragraphs`/`textbook_tasks` рассчитаны на аккуратно разобранный учебник. Для RAG нужны чанки, векторы и **происхождение** (файл, страница, bbox) — иначе учитель не проверит, откуда модель взяла формулу. Для учебника алгебры с формулами это критично.

**Решение.** См. §11 — отдельный пайплайн с очередью верификации человеком.

## 4. Модель данных

### 4.1 Реляционная обвязка

```sql
-- Расширение существующей таблицы
ALTER TABLE ksp_documents ADD COLUMN class_id TEXT REFERENCES classes(id);
ALTER TABLE ksp_documents ADD COLUMN status TEXT NOT NULL DEFAULT 'draft'
    CHECK (status IN ('draft','ready','approved','conducted','archived'));
ALTER TABLE ksp_documents ADD COLUMN language TEXT NOT NULL DEFAULT 'ru'
    CHECK (language IN ('ru','kk'));
ALTER TABLE ksp_documents ADD COLUMN schema_version INTEGER NOT NULL DEFAULT 1;

DROP INDEX IF EXISTS sqlite_autoindex_ksp_documents_1;  -- снять UNIQUE(ktp_lesson_id)
CREATE UNIQUE INDEX uq_ksp_lesson_class ON ksp_documents(ktp_lesson_id, class_id);

-- G10: история версий
CREATE TABLE ksp_revisions (
    id TEXT PRIMARY KEY,
    ksp_id TEXT NOT NULL REFERENCES ksp_documents(id) ON DELETE CASCADE,
    content TEXT NOT NULL,
    author TEXT NOT NULL CHECK (author IN ('user','agent','import')),
    reason TEXT,
    created_at TEXT NOT NULL
);

-- G4: факт проведения
CREATE TABLE ksp_lesson_runs (
    id TEXT PRIMARY KEY,
    ksp_id TEXT NOT NULL REFERENCES ksp_documents(id) ON DELETE CASCADE,
    actual_date TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('planned','conducted','cancelled','postponed')),
```

## 6. Оценивание и дескрипторы

### 6.1 Формативное (G2)

Дескриптор = наблюдаемое действие ученика, привязанное к цели обучения. Баллов нет.

```
Цель 8.2.1.4 «применять теорему Виета»
  ├─ находит сумму и произведение корней          [наблюдение]
  ├─ составляет уравнение по заданным корням      [работа в тетради]
  └─ проверяет корни подстановкой                 [взаимопроверка]
```

**Валидация:** каждый дескриптор ссылается на цель урока; цель без единого дескриптора → предупреждение «цель не проверяется».

### 6.2 Суммативное

Дескриптор = шаг решения с баллом. Структура повторяет существующую `sor_descriptors` (`step_order`, `description`, `points`) — это позволяет переиспользовать спецификации СОР без дублирования.

**Валидация:**
- Σ `points` по этапу = `max_points` этапа;
- `max_points` = `sor_specifications.total_score` (или `soch_specifications.total_score`);
- значение по умолчанию 10 — из конфига, ⚠️ **не хардкод** (как вы и указали);
- для СОЧ допускается больше — ограничение снимается ссылкой на спецификацию, а не константой.

### 6.3 ➕ Связь «цель → дескриптор → задание»

Полный маршрут прослеживается: цель обучения из ТУП → дескриптор в КСП → задание в учебнике (`textbook_task_objectives` уже есть в схеме!). Это даёт MCP возможность отвечать на запрос «подбери задания, закрывающие цель 8.2.1.4 уровня B» и позднее — аналитику «какие цели западают у класса».

## 7. Система валидации

### 7.1 Три уровня строгости

⚠️ В исходной спецификации все проверки равнозначны. Это сделает редактор неработоспособным: учитель не сможет сохранить черновик, пока не заполнит всё.

| Уровень | Поведение | Когда |
|---|---|---|
| 🔴 **BLOCKING** | Нельзя сохранить | Нарушен инвариант целостности |
| 🟡 **WARNING** | Сохранить можно, но статус не поднимется до `ready` | Методическая ошибка |
| 🔵 **HINT** | Информирует | Рекомендация |

### 7.2 Правила

| Код | Правило | Уровень |
|---|---|---|
| V-01 | `ktp_lesson_id` существует, урок не отменён | 🔴 |
| V-02 | Раздел, тема, цели совпадают с КТП | 🔴 (правятся только через КТП) |
| V-03 | Σ `duration_minutes` = `lesson_duration` из конфига | 🔴 |
| V-04 | Каждый этап имеет непустые действия учителя | 🔴 |
| V-05 | Для `summative`: Σ `points` = `max_points` | 🔴 |
| V-06 | `max_points` соответствует спецификации СОР/СОЧ | 🔴 |
| V-07 | Дата КСП совпадает с плановой датой КТП | 🟡 (G7 — дрейф допустим) |
| V-08 | Дата присутствует в расписании класса | 🟡 |
| V-09 | `values_component` заполнен | 🟡 |
| V-10 | Каждая цель урока покрыта хотя бы одним дескриптором | 🟡 |
| V-11 | `formative`-дескрипторы не имеют баллов | 🟡 |
| V-12 | Этап `actualization` ссылается на предыдущий урок | 🟡 |
| V-13 | ДЗ имеет способ проверки | 🟡 |
| V-14 | Порядок этапов методически корректен | 🔵 |
| V-15 | Доля практики ≥ 30 % времени | 🔵 |
| V-16 | Есть дифференциация хотя бы на одном этапе | 🔵 |
| V-17 | Физкультминутка для 1–4 классов | 🟡 (только младшие классы) |
| V-18 | Ресурсы указаны хотя бы для одного этапа | 🔵 |

### 7.3 ➕ Единый валидатор для UI, MCP и экспорта

Валидатор реализуется **один раз в Rust** (`domain/ksp/validation.rs`) и вызывается тремя потребителями: UI (по мере ввода), MCP (перед staging-коммитом), экспорт (перед формированием документа). Это прямой урок из аудита расписания, где Pre-Validator существует в двух несогласованных версиях — Rust и Python — и они расходятся в формулах.

### 9.2 Принципы

| Принцип | Реализация |
|---|---|
| Шапка — только чтение | Наследуемые поля с замком и переходом в КТП (G7) |
| Хронометраж всегда на виду | Липкая полоса с суммой; цвет по состоянию (`43/45` — жёлтый, `47/45` — красный) |
| Этап = сворачиваемый блок | Drag-and-drop переупорядочивание (`@dnd-kit` уже в зависимостях) |
| Два столбца рядом | Действия учителя и ученика — параллельно, как в документе |
| Оценивание — подблок | Показывается только когда `mode ≠ none`; для `summative` появляется счётчик баллов |
| WYSIWYG ограниченный | Жирный, курсив, списки, таблицы, формулы (KaTeX), вставка ресурса. **Без произвольного HTML** |
| Валидация по месту | Ошибка показывается у конкретного блока, а не общим списком сверху |
| Автосохранение | Черновик в `draft` каждые 10 с; версия — при явном сохранении |

### 9.3 ➕ Чего нет в спецификации, но необходимо

- **Панель предпросмотра** — вид документа как при печати, переключатель «редактор / документ».
- **Библиотека шаблонов** (G14) — выбор при создании.
- **Вставка задания из учебника** — поиск по номеру или цели, вставка ссылкой (не копией текста).
- **Боковая панель AI** — предложения агента показываются как дифф с кнопками «применить / отклонить» (G18), а не пишутся сразу в документ.
- **Индикатор готовности** (G16) — чек-лист «можно ли проводить урок».

### 9.4 ⚠️ Риск: WYSIWYG и структурированность конфликтуют

Свободный HTML внутри `teacher_actions` не позволит агенту надёжно править содержимое, а валидатору — проверять. **Решение:** ограниченная схема разметки (подмножество тегов), санитизация на входе и хранение в нормализованном виде. Библиотека — TipTap (ProseMirror) со схемой, ограниченной списком узлов; не `contenteditable` напрямую.

## 11. Пайплайн учебника (отдельный этап)

✅ Вы верно предложили вынести парсинг в отдельную страницу и протестировать на слабом железе. ➕ Разворачиваю в план.

### 11.1 Почему это отдельный проект

Разбор учебника не относится к редактору КСП: это ETL с человеческой верификацией, идущий один раз на учебник и переиспользуемый годами. Смешивать его с редактором — ошибка на уровне архитектуры. Отдельная страница «Библиотека → Разбор учебника» с собственным жизненным циклом.

### 11.2 Схема данных (➕ G20)

```sql
-- Происхождение: без него учитель не проверит формулу
CREATE TABLE textbook_sources (
    id TEXT PRIMARY KEY,
    book_id TEXT NOT NULL REFERENCES textbooks(id) ON DELETE CASCADE,
    file_path TEXT NOT NULL,
    page_count INTEGER NOT NULL,
    parse_status TEXT NOT NULL CHECK (parse_status IN ('pending','running','done','failed')),
    parse_method TEXT NOT NULL CHECK (parse_method IN ('pdf_text','ocr','vlm')),
    created_at TEXT NOT NULL
);

CREATE TABLE textbook_chunks (
    id TEXT PRIMARY KEY,
    book_id TEXT NOT NULL REFERENCES textbooks(id) ON DELETE CASCADE,
    paragraph_id TEXT REFERENCES textbook_paragraphs(id) ON DELETE SET NULL,
    page_number INTEGER NOT NULL,
    bbox TEXT,                      -- координаты на странице
    chunk_type TEXT NOT NULL CHECK (chunk_type IN ('theory','example','task','definition','figure')),
    content_markdown TEXT NOT NULL,
    content_latex TEXT,
    confidence REAL NOT NULL,       -- уверенность извлечения 0..1
    is_verified INTEGER NOT NULL DEFAULT 0,
    verified_by TEXT,
    created_at TEXT NOT NULL
);

CREATE VIRTUAL TABLE textbook_chunks_fts USING fts5(content_markdown, content=textbook_chunks);

-- Векторы отдельно: могут быть перестроены при смене модели
CREATE TABLE textbook_embeddings (
    chunk_id TEXT PRIMARY KEY REFERENCES textbook_chunks(id) ON DELETE CASCADE,
    model TEXT NOT NULL,
    dim INTEGER NOT NULL,
    vector BLOB NOT NULL
);
```

### 11.3 Конвейер

```
PDF/скан
   │
   ├─ 1. Классификация страницы: текстовый слой есть?
   │      ├─ да  → pdfplumber (быстро, точно)          ~0.1 с/стр
   │      └─ нет → OCR tesseract (kaz+rus)             ~2 с/стр
   │
   ├─ 2. Детекция формул и рисунков
   │      формула/схема → Qwen3-VL-4B (только фрагмент, не вся страница!)
   │
   ├─ 3. Структурирование: § → теория / примеры / задания
   ├─ 4. Разбор номеров заданий, уровней (A/B/C), ответов
   ├─ 5. Связывание с целями обучения (textbook_task_objectives)
   ├─ 6. Эмбеддинги (bge-m3 или multilingual-e5-small)
   └─ 7. ➕ ОЧЕРЕДЬ ВЕРИФИКАЦИИ: chunks с confidence < 0.85 → учителю
```

⚠️ **Ключевое решение:** VLM применяется **только к фрагментам с формулами**, а не к каждой странице. Прогон 300-страничного учебника алгебры целиком через Qwen3-VL-4B на слабом ноутбуке займёт часы; выборочный — минуты.

### 11.4 Профили железа

| Профиль | Конфигурация | Стратегия | Оценка на 300 стр. |
|---|---|---|---|
| **Слабый** | 8 ГБ RAM, без GPU | `pdf_text` + OCR; формулы → очередь ручной верификации | ~25 мин, доля ручной работы высокая |
| **Средний** | 16 ГБ RAM, iGPU | + Qwen3-VL-4B **Q4_K_M** через llama.cpp, батч 1, только фрагменты | ~1.5–2 ч |
| **Сильный** | 16+ ГБ RAM, GPU 8 ГБ | Qwen3-VL-4B Q8, батч 4 | ~30 мин |

➕ **Требования к странице разбора:**
- фоновая задача с прогрессом и возможностью остановки (учебник разбирается часами);
- возобновление с прерванной страницы;
- автоопределение профиля железа и предупреждение об ожидаемом времени;
- предпросмотр «страница слева — извлечённое справа» для верификации;
- метрика качества по книге: доля верифицированных чанков.

⚠️ **Учебник не подключается к MCP, пока доля верифицированных чанков ниже порога** (предлагаю 90 % для формульных предметов). Иначе агент будет уверенно цитировать неверно распознанные формулы.
