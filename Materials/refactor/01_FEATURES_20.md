## Блок I. Восстановление продуктового пути (P0)

### Фича 1. Сквозной контракт солвера с единым источником истины

**Проблема сейчас.** Формат обмена Rust ↔ Python описан в трёх независимых местах (`solver/schema.py`, `solver_host.rs`, `types.ts`) и синхронизируется вручную. Rust требует `schema_version == 1`, а `engine.py` возвращает `2` на всех путях, кроме успешного, — поэтому любой INFEASIBLE превращается в техническую ошибку `InvalidContract`. Поля, которые Rust забывает отправить, Pydantic молча заменяет на значения по умолчанию: так и появились дефекты P0-1, P0-2, P1-6.

**Что делаем.**
- Создаём `contracts/solver-v3.schema.json` — единственное нормативное описание `InputModel` и `OutputModel`.
- Pydantic-модели получают `model_config = ConfigDict(extra="forbid")`; Rust-структуры типизируются полностью (`Penalties`, `SolverStats`, `Diagnostics` вместо `serde_json::Value`).
- Вводим `SCHEMA_VERSION` как единую константу; `engine.py` возвращает её на всех ветках, Rust проверяет совместимость диапазона, а не равенство.
- Добавляем golden-фикстуры `contracts/fixtures/{optimal,infeasible,invalid_input,timeout}.json` и CI-job, прогоняющий их обеими сторонами.

**Критерий приёмки.** Удаление любого поля из `input_json` в Rust роняет контрактный тест. Каждый из пяти статусов солвера доходит до React без превращения в ошибку транспорта.

**Файлы.** `contracts/` (новый), `solver/schema.py`, `solver/engine.py`, `solver/__main__.py`, `infra/solver_host.rs`, `.github/workflows/ci.yml`

### Фича 2. Joint-уроки на всём пути UI → солвер → БД

**Проблема сейчас.** Класс-комплекты (ЛУО, ДО, инклюзия) — центральная особенность школы, ради которой сделаны миграции `0018`/`0019` и ограничение `H_joint` в `hard.py:22-48`. Но при запуске из приложения:
1. `schedule_generate` сериализует курикулум без `joint_lesson_id` (`commands/schedule.rs:441-450`) — солвер не знает о спаривании;
2. `validate_hard` (`solver_host.rs:170-185`) считает одного учителя в двух классах нарушением и отвергает решение;
3. INSERT слотов не содержит колонку `joint_lesson_id` (`:502-521`) — спаренность не сохраняется.

Работающая логика существует только в `scripts/update_q4_joint_lessons.py`.

**Что делаем.**
- Передаём `joint_lesson_id` в `curriculum[]`.
- Переписываем `validate_hard`: конфликт учителя/кабинета — только при разных или пустых `joint_lesson_id`.
- Добавляем `joint_lesson_id` в INSERT и в чтение слотов.
- Выражаем инвариант в БД частичным уникальным индексом: дубль допустим только при непустом совпадающем `joint_lesson_id`.
- В `InteractiveGrid` совмещённые уроки визуально помечаются одной группой.

**Критерий приёмки.** Генерация из приложения на боевых данных Q4 даёт то же число совмещённых слотов, что `scripts/verify_luo_and_math_strict_rules.py`. Тест: joint из двух классов размещается в один слот и переживает сохранение и перезагрузку.

**Файлы.** `commands/schedule.rs`, `infra/solver_host.rs`, `migrations/0020_joint_partial_unique.sql`, `db/schedule/slots.rs`, `ui/InteractiveGrid.tsx`

### Фича 3. Закрепления и ручные правки, которые действительно влияют на решение

**Проблема сейчас.** Пользователь может закрепить слот (`schedule_pin_slot`) и перетащить урок мышью (`SchedulePage.tsx:70-92`) — данные ложатся в `schedule_fixed_slots`. Но `schedule_generate` не отправляет `fixed_lessons` в солвер: следующая генерация полностью игнорирует всё, что пользователь зафиксировал. Даже если бы отправляла, матчинг в `hard.py:379-388` берёт первый instance по `(class, subject, teacher)` без учёта подгруппы и номера часа, а `schedule_fixed_slots` сохранила уникальные индексы, несовместимые с joint (`0015:22-27`).

**Что делаем.**
- Читаем фиксации активного варианта и передаём как `fixed_lessons` с `subgroup_label` и `joint_lesson_id`.
- Переписываем H11: сопоставление по полному ключу; конфликт фиксации порождает **именованную диагностику**, а не искусственный `0 == 1`.
- Приводим индексы `schedule_fixed_slots` к joint-совместимому виду.
- В UI: замок на закреплённой ячейке, счётчик «закреплено N уроков» рядом с кнопкой генерации, предупреждение при конфликте фиксаций до запуска солвера.

**Критерий приёмки.** Закреплённый урок присутствует в решении на том же месте. Конфликт двух фиксаций даёт человеко-читаемое сообщение с указанием обеих ячеек, а не «INFEASIBLE».

**Файлы.** `commands/schedule.rs`, `solver/constraints/hard.py`, `migrations/0021_fixed_slots_joint.sql`, `ui/InteractiveGrid.tsx`, `ui/GenerateModal.tsx`

### Фича 4. Переносимый запуск солвера

**Проблема сейчас.** Два критических пути резолвятся через `env!("CARGO_MANIFEST_DIR")` — путь дерева исходников сборочной машины, зашитый в бинарник на этапе компиляции: `solver/__main__.py` (`commands/schedule.rs:479`) и `data/synthetic/` (`:603`). В установленном приложении обоих не существует. Интерпретатор Python ищется по списку, начинающемуся с `C:\Users\imanb\...`; ветка фолбэка возвращает `"python"` **до** какой-либо проверки, поэтому берётся первый попавшийся python без гарантии наличия `ortools`.

**Что делаем.**
- Все ресурсы — через `tauri::path::BaseDirectory::Resource`; `solver/**` и стартовые данные объявляются в `tauri.conf.json → bundle.resources`.
- Обнаружение интерпретатора: кандидат считается годным только если `python -c "import ortools"` завершается кодом 0. Результат кэшируется в состоянии приложения.
- Порядок поиска: переменная `VECTOR_PYTHON` → путь из настроек приложения → встроенный embedded-Python (опционально) → PATH.
- При отсутствии рабочего интерпретатора — экран с инструкцией установки и кнопкой «Указать путь вручную», а не `SolverError::Crashed`.

**Критерий приёмки.** `tauri build`, установка на чистой Windows-машине без Python в PATH → приложение сообщает, чего не хватает; после установки ortools генерация проходит. CI-job `bundle` проверяет наличие `solver/__main__.py` в собранном пакете.

**Файлы.** `infra/solver_host.rs`, `infra/resource_paths.rs` (новый), `tauri.conf.json`, `commands/schedule.rs`, `panels/settings/`

### Фича 5. Управляемый жизненный цикл процесса солвера

**Проблема сейчас.** `GenerateModal` показывает таймер и объявляет проп `onCancelGenerate`, но команды отмены не существует. При таймауте `tokio::time::timeout` возвращает ошибку, а дочерний процесс не убивается (`kill_on_drop` не установлен) — Python с 8 воркерами продолжает занимать все ядра, и повторные запуски накапливают процессы. `stdout` и `stderr` читаются одним `wait_with_output`: при длинном трейсбеке возможно переполнение pipe-буфера и взаимная блокировка до таймаута.

**Что делаем.**
- `Command::kill_on_drop(true)`; хранение `Child` в состоянии приложения; команда `schedule_cancel_generate`, выполняющая `child.kill()`.
- Раздельное асинхронное чтение stdout/stderr в отдельных задачах.
- Прогресс: солвер печатает в stderr строки вида `{"progress": {"objective": N, "elapsed_ms": M}}` из колбэка CP-SAT; Rust транслирует их в UI через `tauri::Emitter`.
- Промежуточное решение при отмене: если найдено `FEASIBLE`, предлагаем сохранить его вместо потери работы.

**Критерий приёмки.** Кнопка «Отмена» останавливает генерацию за ≤ 1 с; в диспетчере задач не остаётся процессов Python. Модальное окно показывает реальное значение целевой функции, а не только прошедшее время.

**Файлы.** `infra/solver_host.rs`, `commands/schedule.rs`, `commands/mod.rs`, `solver/engine.py`, `ui/GenerateModal.tsx`, `domains/schedule/api.ts`

## Блок II. Математическое ядро (P1)

### Фича 6. `SchedulePolicy` — правила школы как данные, а не как код

**Проблема сейчас.** `hard.py` содержит правила одной конкретной школы прямо в теле солвера: «понедельник — только алгебра, вторник — только геометрия» (`:227-233`), «математика запрещена на 6–7 уроках и после 5-го в пн/пт» (`:216-224`), домены предметов заданы литеральными множествами с хеш-идентификаторами Excel-импорта (`xls_9c595eca2c44`, `:153-160`). Правила привязаны к номерам дней: `d == 4` при 6-дневке означает четверг, а не пятницу. Другая школа требует правки исходников математического ядра.

**Что делаем.**
- Расширяем контракт полем `policy`:

```json
{
  "policy": {
    "subject_domains": [
      { "id": "math", "subject_ids": ["algebra", "geometry"], "max_per_day": 1, "pair_if_exceeds": true }
    ],
    "forbidden_placements": [
      { "domain": "math", "periods_from": 5 },
      { "domain": "math", "days": ["MON", "FRI"], "periods_from": 4 }
    ],
    "day_preferences": [
      { "subject_id": "algebra", "require_day": "MON" }
    ],
    "class_rules": { "luo": { "max_period": 5, "no_windows": true } }
  }
}
```

- Дни задаются символами (`MON`…`SAT`), а не индексами: смена длины недели не меняет смысла правил.
- `hard.py` разделяется на `solver/core/` (универсальные ограничения) и `solver/policy/` (интерпретатор политики). В `core` не остаётся ни одного строкового литерала предмета.
- В UI появляется вкладка «Правила школы» — редактор политики.

**Критерий приёмки.** Полный прогон на боевых данных без единого литерала предмета в `solver/core/`. Вторая школа с другим набором правил генерирует расписание, изменив только данные.

**Файлы.** `solver/core/*`, `solver/policy/*` (новые), `solver/schema.py`, `commands/schedule.rs`, `migrations/0022_school_policy.sql`, `ui/PolicyTab.tsx`

### Фича 7. Явная типизация классов и предметов вместо подстрочной магии

**Проблема сейчас.** Спецклассы определяются как `"luo" in cid_lower or "do" in cid_lower` (`hard.py:249-251`). Подстрока `"do"` встречается в множестве обычных идентификаторов — такой класс ошибочно получает запрет 7-го урока, что даёт ложный INFEASIBLE. Домены предметов сопоставляются через `any(s in sid for s in dom_subjs)`: `"math"` совпадает с `"mathematics_extra"`, `"history"` — с `"art_history"`.

**Что делаем.**
- `ClassInput.class_type: Literal["normal", "luo", "do", "inclusive"]` — поле уже есть в БД (миграция `0011`), но не доходит до солвера.
- `SubjectInput.domain: Optional[str]` и `SubjectInput.difficulty_level` вместо угадывания по имени.
- Все сравнения — строгое равенство по идентификатору или домену; подстрочный матчинг удаляется полностью.
- Миграция данных: одноразовый скрипт проставляет `class_type` и `domain` по текущим эвристикам, после чего эвристики удаляются из кода.

**Критерий приёмки.** Класс с идентификатором `9a_dopolnitelnaya_gruppa` не получает ограничений ЛУО. Поиск подстрочных сравнений в `solver/` не даёт результатов.

**Файлы.** `solver/schema.py`, `solver/core/*`, `commands/schedule.rs`, `db/schedule/subjects.rs`, `migrations/0023_subject_domain.sql`, `tools/backfill_class_types.py`

### Фича 8. Честная модель занятости кабинетов

**Проблема сейчас.** Жёсткое ограничение «кабинет занят не более чем одним уроком в слот» (H4b) отключается эвристикой при `instances × rooms × days × periods > 80 000` (`hard.py:293-296`). На боевых 27 классах оценка ≈ 250 000 — то есть **ограничение выключено всегда**, о чём пользователь не уведомляется. Решение с двойным бронированием кабинета затем отвергается `validate_hard` целиком, и генерация проваливается без объяснения. Дополнительно `engine.py:96-108` разрешает фолбэк на любой `General`-кабинет или базовый кабинет учителя, делая `required_room_type` фактически мягким требованием.

**Что делаем.**
- Переформулируем занятость кабинета: вместо `instances × rooms × slots` z-переменных — интервальные переменные и `AddNoOverlap` на ресурс-кабинет, либо канал через `OnlyEnforceIf`. Размер модели падает на порядок, эвристика 80 000 удаляется.
- Фолбэк кабинета становится явным: `SubjectInput.room_fallback: Literal["strict", "general", "any"]`.
- Каждое применение фолбэка порождает запись в `diagnostics.warnings` с кодом `ROOM_FALLBACK_APPLIED` и идентификаторами класса, предмета и кабинета.
- «Пул кабинетов» (несколько кабинетов одного типа) описывается явно, а не выводится из перебора.

**Критерий приёмки.** Тест на 27 классов: ни один кабинет не занят дважды в одном слоте; `validate_hard` проходит без ошибок. Отчёт после генерации перечисляет все случаи фолбэка кабинета.

**Файлы.** `solver/core/rooms.py`, `solver/engine.py`, `solver/schema.py`, `infra/solver_host.rs`

### Фича 9. Единая сетка времени вместо констант в коде

**Проблема сейчас.** Размер сетки задан литералами минимум в четырёх местах: `commands/schedule.rs:354-355` (Pre-Validator, 6×7), `:463-464` (`time_grid` для солвера, 6×7), CHECK-ограничения в миграциях (`day BETWEEN 0 AND 5`, `period BETWEEN 0 AND 7`), и `engine.py:118-123`, где фильтр смен применяется только при `periods_per_day >= 8` — то есть при актуальной сетке 5×7 **не применяется вовсе**, и вторая смена может встать на первый урок. Продукт уже перешёл на 5×7, но UI-путь всё ещё строит 6-дневку.

**Что делаем.**
- Таблица `school_settings`: `days_per_week`, `periods_per_day`, `shift_boundary_period`, расписание звонков.
- Единственный источник — `TimeGrid::from_settings(pool)`; литералов размера сетки в коде не остаётся.
- Логика смен становится безусловной и параметризуется `shift_boundary_period`, а не порогом `>= 8`.
- CHECK в миграциях расширяется до нейтрального диапазона; корректность обеспечивается доменом.
- В UI — редактор сетки с предупреждением о влиянии на существующие варианты.

**Критерий приёмки.** Переключение 5×7 → 6×7 → 6×8 через настройки без изменения кода; вторая смена корректно ограничена при любой сетке.

**Файлы.** `migrations/0024_school_settings.sql`, `domain/schedule/time_grid.rs` (новый), `commands/schedule.rs`, `solver/engine.py`, `ui/SchoolSettings.tsx`

### Фича 10. Ускорение сборки CP-SAT-модели

**Проблема сейчас.** Время до старта решения доминирует над самим решением. Три горячих места:

1. `hard.py:130-140` и `:194-201` — запрет окон между парами уроков реализован четверным вложенным циклом O(P² × k²) на каждую пару (класс, предмет) и каждый день.
2. `hard.py:258-266` — на каждой позиции (class, day, gap) заново фильтруется весь список `instances`. При 27 классах × 5 днях × 6 позициях × ~1 300 instances это порядка 10⁶ холостых итераций. Тот же антипаттерн — в `soft.py:200-206` (S4) и `soft.py:257-262` (S6).
3. `hard.py:298-320` — материализация z-переменных для H4b (см. фичу 8).

**Что делаем.**
- Модуль `solver/indexes.py`: `by_class`, `by_teacher`, `by_class_subject`, `by_class_day` строятся один раз и переиспользуются всеми ограничениями.
- Запрет окон переформулируется через переменную «первый урок пары» и импликации — O(P) вместо O(P²·k²).
- Добавляется бенчмарк построения модели в `solver/tools/benchmark.py` с порогом регрессии в CI.

### Фича 11. Прозрачная диагностика вместо статуса «INFEASIBLE»

**Проблема сейчас.** `build_infeasible_core` (`engine.py:126-196`) собирает причины в одну строку через `"; ".join(reasons)`, а `conflicting_entities` — плоский список идентификаторов без типов. При INFEASIBLE входной JSON нигде не сохраняется — воспроизвести случай невозможно.

**Что делаем.**
- Структурируем диагностику:

```json
{
  "code": "TEACHER_OVERLOAD",
  "severity": "error",
  "message": "Актаева А.Е.: 40 ч/нед, доступно 35 слотов",
  "entities": [{ "type": "teacher", "id": "t_042" }],
```

**Критерий приёмки.** Для каждого из пяти сценариев INFEASIBLE (перегрузка учителя, нехватка кабинета, конфликт split, конфликт фиксаций, превышение слотов класса) пользователь получает конкретную сущность и конкретное действие.

### Фича 12. Единый Pre-Validator

**Проблема сейчас.** Инварианты проверяются дважды и по-разному: `domain/schedule/pre_validate.rs` (Rust, учитывает `joint_lesson_id` при подсчёте физической нагрузки — `:60-100`) и `engine.build_infeasible_core` (Python, joint не учитывает). Две реализации расходятся в формулах, и результат зависит от того, какая сработала первой. Rust-версия к тому же вызывается с захардкоженными `6, 7` вместо реальной сетки и возвращает `Vec<String>` вместо структурированных ошибок.

**Что делаем.**
- Оставляем одну реализацию — Rust `pre_validate`, поскольку она полнее и работает до запуска дорогого процесса.
- Python-версия сводится к тонкой проверке «предусловия, которые может нарушить только сам солвер»; дублирующие формулы удаляются.
- `PreValidationResult` возвращает те же структурированные диагностики, что и фича 11, — единый формат на весь путь.
- Pre-Validator вызывается не только перед генерацией, но и при каждом изменении курикулума: пользователь видит «расписание не решается» до того, как нажмёт «Генерировать».
- Сетка передаётся из `TimeGrid` (фича 9).

**Критерий приёмки.** Rust и Python дают одинаковый вердикт на наборе из 10 заведомо нерешаемых конфигураций. Индикатор готовности данных обновляется в реальном времени на вкладке «Настройки».

**Файлы.** `domain/schedule/pre_validate.rs`, `solver/engine.py`, `commands/schedule.rs`, `ui/ScheduleDashboard.tsx`
