## 1. Резюме для принятия решений

VectorWorkspace — трёхслойное десктоп-приложение (React → Tauri/Rust → Python OR-Tools) для генерации школьного расписания по СанПиН РК. Архитектурная идея здорова: изоляция математики в отдельном процессе, локальная SQLite как единственный источник истины, Pre-Validator как «щит» перед дорогим солвером.

**Однако реализация разошлась с идеей.** Ключевой вывод аудита:

> **Продуктовый путь (React → Rust → solver) и рабочий путь (Python-скрипты → SQLite напрямую) — это два разных, несовместимых приложения. Все результаты последних коммитов (5×7, joint-спаривание, чередование) получены вторым путём. Через UI их воспроизвести нельзя.**

Это не «технический долг в коде», это **раскол архитектуры**. Три подтверждения:

| Факт | Где | Следствие |
|---|---|---|
| `schedule_generate` не передаёт `joint_lesson_id` в солвер | `commands/schedule.rs:441-450` | Класс-комплекты (ЛУО/ДО) через UI не спариваются вообще |
| `schedule_generate` не передаёт `fixed_lessons` | `commands/schedule.rs:452-478` | Кнопка «закрепить слот» в UI не влияет на генерацию |
| `validate_hard` запрещает одного учителя в двух классах одновременно | `infra/solver_host.rs:170-185` | Даже если бы joint-уроки дошли до солвера, результат был бы отвергнут как «Hard violation» |

**Вторая по важности проблема** — приложение не собирается в дистрибутив: два критических пути (`solver/__main__.py` и `data/synthetic/`) резолвятся через `env!("CARGO_MANIFEST_DIR")`, то есть через путь машины разработчика, зашитый в бинарник на этапе компиляции.

**Третья** — школьные правила одной конкретной школы (запрет алгебры по вторникам, идентификаторы вида `xls_9c595eca2c44`, подстрока `"luo"` в id класса) вкомпилированы в `solver/constraints/hard.py`. Продукт не переносится на вторую школу без правки исходников солвера.

Оценка объёма: **P0-блокеры — ~5–7 рабочих дней**, полный переход на целевую архитектуру — **4–6 недель**.

## 2. Карта системы «как есть»

### 2.1 Заявленный поток данных (OPENSPEC.md §1.2)

```
[React UI] ──Tauri IPC──> [Rust src-tauri] ──Pre-Validator──> [Python OR-Tools CP-SAT]
     ▲                          │                                      │
     └──────(vector.db)─────────┴──────(Save Schedule JSON & DB)───────┘
```

### 2.2 Фактический поток данных

```
                     ┌─────────────────────────────────────────┐
 ПУТЬ A (UI)         │  React SchedulePage                     │
 неполный,           │      ↓ scheduleApi.generate()           │
 частично сломан     │  Rust schedule_generate                 │
                     │      ↓ (теряет joint/fixed/previous)    │
                     │  solver/__main__.py                     │
                     │      ↓ (schema_version=2 ⇒ отказ Rust)  │
                     │  validate_hard ⇒ ошибка на joint        │
                     └─────────────────────────────────────────┘
                                        ✗ не сходится

                     ┌─────────────────────────────────────────┐
 ПУТЬ B (скрипты)    │  scripts/update_q4_joint_lessons.py     │
 рабочий, но         │      ↓ строит InputModel вручную        │
 вне продукта        │  solver.engine.solve()  (import)        │
                     │      ↓                                  │
                     │  sqlite3.connect(...) ── UPDATE/INSERT  │
                     │      ↓ прямо в vector.db, мимо Rust     │
                     │  scripts/verify_*.py                    │
                     └─────────────────────────────────────────┘
                                        ✔ даёт результаты в коммитах
```

**22 скрипта** открывают `vector.db` напрямую через `sqlite3.connect`, обходя доменные инварианты, транзакционную обёртку, бэкапы (`db::backup_database`) и `PRAGMA foreign_keys`.

### 2.3 Инвентарь модулей

| Слой | Модули | LOC | Оценка |
|---|---|---:|---|
| Python solver | `engine.py`, `constraints/hard.py`, `constraints/soft.py`, `schema.py` | ~1 310 | Ядро ценности, но перегружено хардкодом |
| Rust commands | `commands/schedule.rs` (+ ktp, tup, identity) | ~2 460 | `schedule.rs` — божественный модуль на 1 218 строк |
| Rust domain | `domain/schedule/*`, `domain/tup.rs`, `domain/ktp.rs` | ~1 440 | Самый здоровый слой; недоиспользован |
| Rust infra | `tup_html_parser.rs` (1 423), `tup_parser.rs` (1 358), `solver_host.rs` | ~3 900 | Два парсера-монолита, дублирующие друг друга |

### P0 — блокеры

| # | Дефект | Локация | Механизм отказа |
|---|---|---|---|
| **P0-1** | `joint_lesson_id` не передаётся в солвер | `commands/schedule.rs:441-450` | Курикулум сериализуется без поля; класс-комплекты рассыпаются на независимые уроки. Вся логика `H_joint` в `hard.py:22-48` — мёртвый код при запуске из UI |

| **P0-5** | Пути ресурсов зашиты на этапе компиляции | `commands/schedule.rs:479` и `:603` | `env!("CARGO_MANIFEST_DIR")` указывает на дерево исходников сборочной машины. | **P0-6** | Интерпретатор Python зашит на конкретного пользователя | `solver_host.rs:41-42` | Первый кандидат — `C:\Users\imanb\...`. ## 4. Слой 1: Контракт Rust ↔ Python

### 4.1 Текущее состояние

Контракт описан трижды и нигде не проверяется автоматически:

| Определение | Файл | Тип |
|---|---|---|
| `InputModel` / `OutputModel` | `solver/schema.py` | Pydantic v2 |
| `SolverOutput` | `Desktop/src-tauri/src/infra/solver_host.rs:22-30` | serde, поля `serde_json::Value` |
| `ScheduleGenerateResult` | `Desktop/src/types.ts` | TS-интерфейс |

Rust-сторона намеренно ослаблена: `solver_stats`, `penalties`, `diagnostics` объявлены как `serde_json::Value`. Это значит, что **любое расхождение схем обнаруживается только в рантайме у пользователя**.

### 4.2 Конкретные расхождения

```
Rust отправляет                     Python ожидает            Результат
─────────────────────────────────────────────────────────────────────────
schema_version: 2                   Literal[1,2]              ok
curriculum[].joint_lesson_id: ✗     Optional[str]             тихо None ⇒ P0-1
fixed_lessons: ✗ (нет ключа)        default_factory=list      тихо [] ⇒ P0-2
previous_grid: ✗                    Optional[dict]            тихо None ⇒ P1-6
time_grid: 6×7                      ge=1,le=7 / ge=1,le=10    валидно, но неверно ⇒ P1-5

Python возвращает                   Rust требует              Результат
─────────────────────────────────────────────────────────────────────────
schema_version: 1 (успех)           == 1                      ok
schema_version: 2 (INFEASIBLE)      == 1                      ОТКАЗ ⇒ P0-3
penalties.change_slot               Penalties без поля        отброшено валидацией
```

Обратите внимание: **все несоответствия «тихие»** — Pydantic по умолчанию подставляет значения для отсутствующих optional-полей, а не падает. Именно поэтому P0-1 и P0-2 прожили несколько релизов незамеченными.

### 4.3 Требования к целевому контракту

- **SPEC-C1.** Единственный источник истины — JSON Schema в `contracts/solver-v3.schema.json`. Pydantic-модели и Rust-структуры генерируются или валидируются против неё в CI.
- **SPEC-C2.** Rust-сторона типизирует `penalties`, `solver_stats`, `diagnostics` полноценными структурами, а не `serde_json::Value`.
- **SPEC-C3.** `additionalProperties: false` в схеме и `extra="forbid"` в Pydantic — отсутствующее или лишнее поле должно быть громкой ошибкой, а не молчаливым дефолтом.
- **SPEC-C4.** Единая константа `SCHEMA_VERSION` на всех путях возврата; в Rust — проверка диапазона совместимости, а не равенства.
- **SPEC-C5.** Golden-тест контракта: фикстуры `contracts/fixtures/*.json` прогоняются и Rust-, и Python-стороной в CI.

## 5. Слой 2: Математическое ядро (CP-SAT)

### 5.1 Структурная проблема: правила школы внутри движка

`solver/constraints/hard.py` содержит 13 логических блоков, из которых **три — правила конкретной школы**, а не универсальные ограничения:

| Блок | Строки | Универсальность |
|---|---|---|
| H1 «ровно один слот» | 15-20 | универсальное |
| H_joint | 22-48 | универсальное |
| H2 «учитель ≤ 1» | 52-71 | универсальное |
| H3 «класс ≤ 1» | 73-102 | универсальное |
| H_spread_daily | 104-140 | параметризуемое (порог = `days`) |
| H_subject_domains | 142-201 | **данные школы** (списки id) |

### 5.2 Проблема производительности

Построение модели — не решение — доминирует по времени. Три горячих места:

**(а) Квадратичный запрет окон между парами уроков.** `hard.py:130-140` и `:194-201`:

```python
for p1 in range(periods):
    for p2 in range(p1 + 2, periods):
        for x1 in period_map.get(p1, []):
            for x2 in period_map.get(p2, []):
                model.Add(x1 + x2 <= 1)
```

Для каждой пары (класс, предмет) и каждого дня — O(P² × k²) добавлений ограничений. Эквивалентный результат достигается переменной «старт пары» и импликациями за O(P).

**(б) Пересборка списков внутри тройного цикла.** `hard.py:258-266` — на каждом (class, day, gap) полный проход по `instances`:

```python
vars_before = [x[(inst["idx"], d, pb)] for inst in instances
               if inst["class_id"] == cid for pb in range(0, p_gap) if ...]
```

При 27 классах × 5 дней × 6 gap-позиций × ~1 300 instances это порядка 10⁶ холостых итераций. Лечится предвычисленным индексом `instances_by_class`. Тот же антипаттерн — в `soft.py:200-206` (S4) и `soft.py:257-262` (S6).

**(в) Материализация z-переменных для H4b.** `hard.py:298-320` создаёт до `instances × rooms × days × periods` булевых переменных. Канал `x ∧ y` выражается через `OnlyEnforceIf`, а сама занятость кабинета — через `AddNoOverlap` по ресурсу.

### 5.3 «Тихие» решения движка

Три места, где солвер **молча меняет постановку задачи**:

1. `hard.py:293-296` — H4b (кабинет ≤ 1 занятие в слот) отключается по эвристике на 80 000 переменных. Пользователь не уведомляется, а жёсткое ограничение превращается в отсутствующее.
2. `engine.py:118-123` — фильтр смен применяется только при `periods_per_day >= 8`.
3. `engine.py:96-108` — фолбэк кабинета: если специализированный тип не найден, разрешается любой `General` **или базовый кабинет учителя**. Требование `required_room_type` де-факто мягкое.

Любое ослабление постановки обязано попадать в `diagnostics.warnings` — сейчас туда пишутся только два вида предупреждений (`engine.py:222-243`).

### 5.4 Требования к целевому ядру

- **SPEC-S1.** Правила школы выносятся в `InputModel.policy`: домены предметов, запрещённые пары (день, урок) для предмета/домена, флаг «класс без окон», флаг «нет N-го урока». `hard.py` перестаёт содержать строковые литералы предметов.
- **SPEC-S2.** Классификация классов и предметов — по явным полям (`ClassInput.class_type`, `SubjectInput.domain`), а не по подстроке в идентификаторе.
- **SPEC-S3.** Любое ослабление ограничения (пропуск H4b, отключение смен, фолбэк кабинета) обязано порождать запись в `diagnostics.warnings` с машиночитаемым кодом.
- **SPEC-S4.** Построение модели — не более O(instances × days × periods); все выборки идут через предвычисленные индексы.
- **SPEC-S5.** Каждое ограничение H* и S* покрыто парой тестов: «нарушение обнаруживается» и «валидное решение не отвергается».
- **SPEC-S6.** S5 (movement) либо реализуется, либо удаляется из `Weights`, БД и UI. Заглушка, замаскированная под функцию, недопустима.

## 6. Слой 3: Rust-бэкенд и слой команд

### 6.1 Нарушение объявленной слоистости

`.agents/AGENTS.md` и `docs/02-domain-architecture.md` декларируют схему `commands → domain → db/infra`. Фактически `commands/schedule.rs` обходит `domain` почти везде:

- `schedule_get_state:44-60` — сырой `sqlx::query_as` по `schedule_classes` прямо в команде;
- `schedule_generate:337-341` — то же самое;
- `schedule_import_legacy:597-973` — 377 строк ETL: чтение JSON с диска, upsert учителей/кабинетов/классов/предметов, вычисление `teacher_subjects`, инференс типов кабинетов, создание вариантов;
- `schedule_export:533-578` — сборка XLSX и кодирование base64.

Слой `domain/schedule/` при этом содержит только `model.rs` (272), `pre_validate.rs` (359), `validation.rs` (196) — то есть валидацию, но не бизнес-операции.

### 6.2 Pre-Validator: правильная идея, неполная реализация

`pre_validate.rs` — сильное место проекта: он умеет считать физическую нагрузку учителя с учётом `joint_lesson_id` (`:60-100`), чего сам солвер по UI-пути даже не видит. Но:

- вызывается с захардкоженными `6, 7` (`commands/schedule.rs:354-355`), а не с реальной сеткой;
- возвращает `Vec<String>` вместо структурированных ошибок с кодами и идентификаторами сущностей — фронт не может подсветить конкретного учителя;
- дублирует логику `engine.build_infeasible_core` (`engine.py:126-196`), но с другими формулами: Rust учитывает joint, Python — нет. **Две разные правды об одном инварианте.**

### 6.3 Управление процессом солвера

`solver_host.rs:90-110`:

```rust
let output = tokio::time::timeout(timeout, child.wait_with_output()).await
    .map_err(|_| SolverError::Timeout)?
```

При таймауте `child` дропается, но `tokio::process::Child` по умолчанию **не убивает** процесс при дропе (`kill_on_drop` не установлен). Python с `num_workers=8` продолжает занимать все ядра. При повторных попытках генерации процессы накапливаются.

Дополнительно: `stderr` читается вместе со `stdout` одним `wait_with_output`; при длинном трейсбеке и заполнении pipe-буфера возможна взаимная блокировка до срабатывания таймаута.

### 6.4 Требования

- **SPEC-R1.** `commands/*` — только парсинг DTO, вызов сервиса домена, маппинг ошибки. Целевой размер команды — до 30 строк.
- **SPEC-R2.** `schedule_import_legacy` переносится в `infra/schedule_import.rs` как явная операция «импорт каталога» с путём, выбранным пользователем, а не автозапуск.
- **SPEC-R3.** Единый `ScheduleError` (`thiserror`) с кодами; `Result<T, ScheduleError>`, сериализуемый в структурированный объект для фронта.
- **SPEC-R4.** `SolverHost` владеет процессом: `kill_on_drop(true)`, раздельное чтение stdout/stderr, отменяемость через `CancellationToken`, события прогресса в UI через `tauri::Emitter`.
- **SPEC-R5.** Все пути к ресурсам — через `tauri::path::BaseDirectory::Resource`; `solver/` и стартовые данные объявляются в `tauri.conf.json → bundle.resources`.
- **SPEC-R6.** Обнаружение Python: проверка кандидата запуском `python -c "import ortools"`, а не по существованию файла; результат кэшируется; при отсутствии — внятная ошибка с инструкцией вместо `Crashed`.
- **SPEC-R7.** Единый источник `TimeGrid` — таблица настроек школы; `days`/`periods_per_day` не встречаются как литералы в коде.

## 7. Слой 4: Данные и миграции SQLite

### 7.1 Инварианты БД отстали от продукта

| Инвариант в схеме | Актуальность |
|---|---|
| `day INTEGER CHECK (day BETWEEN 0 AND 5)` (`0010`, `0013`, `0019`) | Жёстко зашита 6-дневка. Переход на 5×7 не отражён; переход на другую сетку невозможен без миграции |
| `period INTEGER CHECK (period BETWEEN 0 AND 7)` | Зашиты 8 уроков; `engine.py` работает с 7 |
| `hours_per_week CHECK BETWEEN 1 AND 6` (`0010`) | Дублирует `Field(ge=1, le=6)` в `schema.py` — два места для одного правила |
| `room_type CHECK IN (...)` — 8 литералов | Справочник в виде CHECK: добавление типа кабинета = миграция |
| `UNIQUE (class_id, subject_id)` в `schedule_curriculum` | Класс не может иметь два разных курса одного предмета (например, деление на группы разными учителями сверх split) |

### 7.2 Миграция 0019 сняла защиту, ничего не дав взамен

`0019_joint_slot_uniques.sql` удаляет `UNIQUE(teacher_id, day, period, variant_id)` и `UNIQUE(room_id, day, period, variant_id)`, чтобы разрешить класс-комплекты. Но:

- корректный инвариант — «дубликат учителя в слоте допустим **только** при совпадающем непустом `joint_lesson_id`» — не выражен нигде: ни частичным индексом, ни триггером;
- следовательно, любая ошибка записи (в том числе из скрипта) даёт настоящую накладку, которую БД примет молча;
- `schedule_fixed_slots` при этом сохранила старые уникальные индексы (`0015:22-27`) — **закрепить joint-урок физически невозможно**;
- миграция выполняется с `PRAGMA foreign_keys = OFF` без последующего `foreign_key_check` — осиротевшие строки не выявляются.

### 7.3 Отсутствует история и аудит

`schedule_slots` перезаписывается целиком при каждой генерации (`commands/schedule.rs:494-499`). Нет:

- журнала запусков (когда, с какими весами, каким seed, за сколько мс, с каким objective);
- воспроизводимости: по варианту нельзя восстановить входные данные, породившие расписание;
- ручных правок как отдельной сущности — drag&drop пишется в `schedule_fixed_slots`, но нет пометки «правка пользователя поверх решения».

### 7.4 Требования

- **SPEC-D1.** `days`/`periods` — данные (таблица `school_settings`), не CHECK-константы. CHECK заменяется на широкий диапазон либо на FK к таблице расписания звонков.
- **SPEC-D2.** Инвариант joint выражается частичным уникальным индексом:
  `CREATE UNIQUE INDEX ... ON schedule_slots(teacher_id, day, period, variant_id) WHERE joint_lesson_id IS NULL;` — и аналогично для кабинета.
- **SPEC-D3.** `schedule_fixed_slots` получает те же joint-совместимые индексы.
- **SPEC-D4.** Новая таблица `schedule_runs`: `id, variant_id, started_at, finished_at, status, objective, penalties_json, weights_json, seed, input_hash, solver_version`.
- **SPEC-D5.** Каждая миграция, отключающая FK, завершается `PRAGMA foreign_key_check` с падением при ненулевом результате.
- **SPEC-D6.** Справочники (`room_type`, `class_type`, `shift`) выносятся в таблицы с FK.

## 8. Слой 5: Фронтенд (React/TS)

### 8.1 Два API-слоя, ноль абстракции

`services/api.ts` и `domains/schedule/api.ts` содержат идентичную обёртку `call<T>` с разным текстом ошибки. Ни один из них не:

- нормализует регистр: в `services/api.ts` бэкенд отдаёт camelCase, в `schedule/api.ts` — snake_case; в `types.ts` живут оба стиля;
- типизирует ошибки (везде `String(e)`);
- поддерживает отмену (`AbortSignal`), ретраи, дедупликацию запросов.

`upsertClass` и `importLegacy` возвращают `Promise<unknown>` — типобезопасность отсутствует именно там, где мутируются данные.

### 8.2 Состояние страницы расписания

`SchedulePage.tsx` держит 12 единиц состояния в `useState` и перезагружает **всё состояние** (`scheduleApi.getState()` — учителя, кабинеты, классы, предметы, курикулум, веса, слоты, варианты, фиксации) после каждой операции: pin, unpin, drag&drop. При 27 классах × 5×7 это сотни килобайт через IPC на каждое перетаскивание.

Побочный эффект внутри `load()` (`:98-110`) — автоимпорт чужих данных (P1-11) — прячет мутацию БД в функции загрузки.

### 8.3 Требования

- **SPEC-F1.** Один `ipc.ts` с типизированным `invoke`, единой нормализацией регистра и единым классом ошибки.
- **SPEC-F2.** Типы генерируются из Rust (`ts-rs` или `specta`), а не пишутся руками в `types.ts`.
- **SPEC-F3.** Мутации возвращают дельту, а не сигнал «перезагрузи всё»; локальное состояние обновляется точечно.
- **SPEC-F4.** Побочные эффекты, изменяющие БД, вызываются только по явному действию пользователя.
- **SPEC-F5.** `DesignSandbox` выносится за пределы продакшн-бандла (dev-only маршрут либо отдельная точка входа Vite).

## 9. Слой 6: Скрипты — «теневой бэкенд»

### 9.1 Масштаб

41 Python-скрипт и 6 JS-скриптов в `scripts/`. Из них **22 подключаются к `vector.db` напрямую**. Категории:

| Категория | Примеры | Проблема |
|---|---|---|
| Мутирующие БД | `reseed_sqlite_db.py`, `fix_joint_math_and_alternating.py`, `apply_all_joint_and_related_fixes.py`, `apply_migration_0019_test.py` | Обходят миграции sqlx, бэкапы, доменные инварианты. `apply_migration_0019_test.py` применяет миграцию **вручную** — состояние `_sqlx_migrations` расходится с реальной схемой |
| Генерирующие расписание | `update_q4_joint_lessons.py`, `generate_variant3.py`, `rebalance_5day.py`, `rebuild_curriculum_5day.py` | Дублируют логику `schedule_generate`, но полнее её (joint, 5×7). Это и есть настоящий продакшн-путь |
| Проверяющие | `verify_*.py` (5 шт.), `check_*.py` (5 шт.), `analyze_*.py`, `inspect_*.py` (5 шт.) | Одноразовые отладочные срезы, зафиксированные в репозитории; дублируют друг друга (`check_db.py` / `check_db_windows.py`) |
| Импорт/экспорт | `import_schedule_from_excel.py`, `generate_schedule_template_excel.py` (727 строк) | Крупная функциональность, недоступная из продукта |

### 9.2 Почему это критично

Скрипты — не вспомогательный инструмент, а **параллельная реализация продукта**. Последние три коммита (`22c3080`, `cbf3fa4`, `26d2928`) описывают результаты, полученные скриптами; UI этих результатов воспроизвести не может. Пока это так, любое утверждение вида «расписание генерируется корректно» относится к скриптам, а не к приложению.

Существующий страж `scripts/audit_db_scripts.py` защищает только таблицу `tup_documents` — на `schedule_*` он не распространяется.

### 9.3 Требования

- **SPEC-U1.** Скрипты делятся на три каталога: `tools/` (поддерживаемые CLI), `scripts/oneoff/` (архив, исключён из CI и линта), `scripts/verify/` (превращаются в pytest-тесты).
- **SPEC-U2.** Логика генерации из `update_q4_joint_lessons.py` переносится в `generation_service`; скрипт становится тонкой обёрткой над тем же кодом.
- **SPEC-U3.** Прямые `sqlite3.connect` к боевой БД запрещены; доступ — через общий модуль `tools/db.py`, снимающий бэкап и включающий `foreign_keys`.
- **SPEC-U4.** `audit_db_scripts.py` расширяется на все таблицы `schedule_*` и `ktp_*`.

### 10.2 Пробелы CI

`.github/workflows` содержит три job: `frontend`, `rust`, `db-scripts`. **Нет job для `pytest solver/tests`** — то есть математическое ядро, главный носитель ценности, не проверяется ни одним автоматическим прогоном.

- нет `cargo clippy` / `cargo fmt --check`;
- нет `eslint`;

Логирование отсутствует как подсистема: разрозненные `println!`/`console.error`, нет `tracing`, нет файла лога, нет уровней. При INFEASIBLE у пользователя нет ничего, кроме строки `reason`. Воспроизвести проблему невозможно — входной JSON солвера нигде не сохраняется.

### 10.4 Требования

- **SPEC-T1.** CI job `solver`: `pip install -r solver/requirements.txt && pytest solver/tests -q`.
- **SPEC-T2.** Тесты, которые самоотключаются при отсутствии окружения, запрещены: либо окружение обеспечивается, либо тест помечается `#[ignore]` явно.

- **SPEC-T4.** Job `bundle`: `tauri build` на Windows-раннере со smoke-запуском солвера из собранного пакета.
- **SPEC-T5.** `tracing` в Rust с ротацией в файл в `app_log_dir`; входной и выходной JSON солвера сохраняются рядом с логом при статусе INFEASIBLE/TIME_LIMIT.

```
│    core/      — универсальные H1..H11, S1..S7 (без литералов)    │
│    policy/    — интерпретатор InputModel.policy                  │
│    engine.py  — сборка, решение, диагностика                     │
│    indexes.py — предвычисленные индексы (по классу/учителю/дню)  │
└──────────────────────────────────────────────────────────────────┘
```

**Ключевые границы:**

1. `contracts/` — единственное место, где описан формат обмена. Изменение схемы без обновления обеих сторон роняет CI.
2. `SchedulePolicy` — правила школы приходят данными. `solver/core` не знает слов «алгебра», «ЛУО», «пятница».
3. `scripts/` теряет право писать в БД; генерация доступна только через `generation_service` — из UI или из `tools/`-CLI, вызывающего тот же код.

## 13. Метрики готовности

| Критерий | Проверка |
|---|---|
| Класс-комплекты работают из UI | Генерация из приложения даёт то же число окон, что `scripts/verify_luo_and_math_strict_rules.py` |
| Закрепления влияют на результат | Закреплённый слот присутствует в решении; тест в CI |
| INFEASIBLE доносится до пользователя | Ни один статус не превращается в `InvalidContract`; тест на каждый статус |
| Дистрибутив работает | `tauri build` → установка на чистой машине → генерация проходит |
| Продукт переносим на вторую школу | Полная генерация без единой правки `solver/` |
| Ядро под тестами | `pytest solver/tests` в CI зелёный; покрытие `hard.py`/`soft.py` ≥ 80 % |
| Нет теневого бэкенда | Поиск `sqlite3.connect` в `scripts/` не находит боевую БД |
| Скорость сборки модели | Построение модели для 27 классов ≤ 3 с (сейчас доминирует над временем решения) |
| Ошибки типизированы | Ни одной команды с `Result<_, String>` |
| Один источник контракта | Изменение схемы без синхронизации роняет CI |
