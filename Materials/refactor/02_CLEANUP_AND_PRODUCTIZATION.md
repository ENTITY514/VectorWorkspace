## 1. Диагноз: как появился теневой бэкенд

Скрипты в `scripts/` появлялись не по злому умыслу — каждый решал реальную задачу, которую **продукт не умел решать**. Механизм всегда один и тот же:

```
Нужна фича  →  в UI её нет  →  пишем скрипт напрямую в SQLite  →  фича «готова»
                                          ↓
                          продукт не научился ничему,
                          а состояние БД теперь недостижимо через UI
                                          ↓
                          следующая задача → снова скрипт
```

Через 41 итерацию этого цикла получилось то, что есть сейчас: **приложение — это витрина, а работу выполняют скрипты**. Подтверждения:

| Наблюдение | Что это значит |
|---|---|
| 22 скрипта пишут в `vector.db` через `sqlite3.connect` | Продуктовый бэкенд обойдён; инварианты, бэкапы и миграции не участвуют |
| `update_q4_joint_lessons.py` полнее, чем `schedule_generate` | Логика генерации существует в двух версиях, и продуктовая — младшая |
| 6 скриптов ссылаются на `C:\Projects\VectorWorkspace` | Проект давно переехал на `E:\`; эти скрипты **физически не запускаются** и всё равно лежат в репозитории |
| `verify_*.py` захардкожены на `variant_id='v3_q4'` | Это не тесты, а разовые срезы одного конкретного прогона |
| `check_teacher_loads.py` ищет `LIKE '%радионова%'` | Отладка одного случая, зафиксированная в репозитории навсегда |
| 15 файлов `__pycache__` в git, `.gitignore` их не содержит | Гигиена репозитория отсутствует как практика |

**Главное следствие.** Пока продукт не умеет того, что умеют скрипты, удалять скрипты нельзя — потеряется работоспособность. Поэтому чистка обязана идти **парами**: «удаляем скрипт X» ↔ «продукт научился делать X». Документ построен именно так: раздел 3 говорит, что удалить, раздел 7 — что должно появиться взамен.

## 2. Правило сортировки

Каждый файл попадает ровно в одну из четырёх категорий:

| Категория | Признак | Действие |
|---|---|---|
| 🗑️ **УДАЛИТЬ** | Одноразовый; сломан; дублирует другой; отладка конкретного случая | `git rm`, без замены |
| 🔧 **В ПРОДУКТ** | Делает то, что обязано быть функцией приложения | Логику перенести в Rust/UI, скрипт удалить |
| 🧪 **В ТЕСТ** | Проверяет инвариант, который должен проверяться всегда | Переписать как pytest, скрипт удалить |
| ✅ **ОСТАВИТЬ** | Поддерживаемый инструмент разработчика с документацией | Перенести в `tools/`, привести к стандарту |

**Критерий «одноразовости»:** если скрипт содержит имя конкретного учителя, идентификатор конкретного варианта или абсолютный путь — он одноразовый по определению.

### 3.5 🧪 Превратить в тесты

Эти скрипты проверяют инварианты, которые обязаны проверяться при каждом изменении солвера, а не вручную после каждого прогона. Сейчас они захардкожены на `variant_id='v3_q4'` и работают по боевой БД — это делает их непригодными как тесты, но их **логика проверки корректна и ценна**.

| Файл | Строк | Проверяет | Становится |
|---|---:|---|---|
| `scripts/verify_all_student_windows.py` | 30 | Отсутствие окон у всех классов | `solver/tests/test_no_student_windows.py` |

**Как переписать:** вместо чтения боевой БД тест берёт фикстуру из `contracts/fixtures/`, вызывает `solve()` и проверяет свойство решения. Тест становится частью CI-job `solver` (см. фичу SPEC-T1 в аудите).

**Действие:** переписать как pytest, исходные скрипты удалить.

## 9. Барьеры: чтобы мусор не вернулся

Разовая чистка бесполезна без правил, которые не дадут циклу из §1 повториться.

### 9.1 Технические барьеры (проверяются автоматически)

| Барьер | Реализация |
|---|---|
| Прямой доступ к боевой БД запрещён | `tools/db.py` отказывается работать с путём внутри `%APPDATA%` без флага `--i-know-what-i-am-doing`; CI ищет `sqlite3.connect` вне `tools/db.py` и падает |
| Скрипты не мутируют схему | `audit_db_scripts.py` расширяется на `schedule_*`, `ktp_*`; требует маркеров `UNIQUENESS_VERIFIED` и `BACKUP_TAKEN` |
| Абсолютные пути запрещены | CI-проверка: поиск `C:\`, `E:\`, `/Users/` в `scripts/`, `tools/`, `solver/`, `src-tauri/src/` |
| Имена людей не попадают в код | CI-проверка на кириллические ФИО в `solver/` и `src-tauri/src/` |
| Артефакты не коммитятся | `.gitignore`: `__pycache__/`, `*.pyc`, `scratch/`, `*.db`, `*.db.bak.*`, `.pytest_cache/` |
| Мёртвые команды не проходят | Генерация TS-типов из Rust (фича 19): вызов незарегистрированной команды ломает `tsc` |

### 9.2 Организационные правила

1. **Правило одного пути.** Любое изменение состояния расписания проходит через `generation_service`. Если что-то нельзя сделать через продукт — это дефект продукта, а не повод писать скрипт.
2. **Скрипт — это заявка на фичу.** Возникла потребность в разовом скрипте? Сначала заводится задача «продукт не умеет X». Скрипт живёт в `scripts/oneoff/` (вне CI) до закрытия задачи и удаляется вместе с ней.
3. **Правило имени.** Файл, содержащий имя человека, идентификатор конкретного варианта или абсолютный путь, не может быть закоммичен в `tools/` или `solver/`.
4. **Каталог `scripts/oneoff/`** — единственное легальное место для одноразового кода; исключён из CI, линта и обзора; чистится раз в спринт без обсуждения.

### 9.3 Целевая структура

```
tools/            ← поддерживаемые CLI (docstring, argparse, тесты)
scripts/oneoff/   ← карантин, вне CI, чистится каждый спринт
solver/tests/     ← сюда переезжают все verify_*
fixtures/         ← демо-данные и контрактные фикстуры
contracts/        ← схема обмена Rust ↔ Python
backup/           ← вне git; эталоны и копии БД
```
