# План Реализации: Ядро Модели Школы и Интеграция Supabase

Цель: Создать прочный фундамент базовой модели школы (роли, структура) и настроить облачную синхронизацию через Supabase для работы с разных устройств.

---

## 1. Архитектура Синхронизации (Local-First + Supabase)

Ранее проект напрямую общался с Supabase из React (в `KTPHUB`). Это приводило к задержкам загрузки, жесткой привязке к интернету и смешиванию логики БД с UI. Мы больше **не будем** этого делать.

**Предлагаемый подход (Local-First):**
1. **Единый источник истины (Священный Грааль):** Локальная база данных `SQLite` через Rust-бэкенд. React-фронтенд общается *только* с локальным Rust-ядром. Приложение всегда работает мгновенно и доступно без интернета.
2. **Фоновая Синхронизация (Sync Engine):** Rust-бэкенд получает фоновый процесс (Background Worker). Раз в N минут (или по кнопке "Синхронизировать") Rust подключается к `Supabase` (через HTTP/REST), скачивает изменения с сервера и отправляет локальные изменения.
3. **Разрешение конфликтов:** По правилу "Последний записавший побеждает" (Last Write Wins) на основе поля `updated_at`.

## 2. Проектирование Базовой Модели (School Core Model)

В БД SQLite (и зеркально в Supabase) необходимо создать фундамент.

### Таблицы и Сущности

**A. `schools` (Школа)**
- `id` (UUID)
- `name` (Название школы, например "Школа-лицей №1")
- `region`, `address`
- `created_at`, `updated_at`

**B. `roles` (Ролевая модель)**
Жесткий Enum (или справочная таблица), определяющий уровень доступа:
1. `teacher` (Обычный учитель — доступ только к своим КТП и своим классам).
2. `mo_head` (Руководитель МО — доступ к КТП своего методического объединения).
3. `head_teacher` (Завуч — доступ ко всему учебному процессу, создание матрицы расписания).
4. `educator` (Воспитатель / Классный руководитель — доступ к журналам своего класса).
5. `admin` (Администратор системы/директор).

**C. `staff` (Сотрудники / Пользователи)**
- `id` (UUID, привязан к Supabase Auth UID)
- `school_id` (FK -> schools)
- `full_name`
- `role` (Enum)
- `subject_specialization` (Специализация — математика, физика и т.д.)
- `is_active` (Булево, если сотрудник уволен — логическое удаление)

**D. `mo_departments` (Методические Объединения)**
- `id`
- `school_id`
- `name` (например, "МО Точных наук")
- `head_id` (FK -> staff.id, руководитель МО)

## 3. План Действий (Roadmap)

### Фаза 1: Схема Базы Данных (Rust SQLite)
- Добавить миграции SQL для таблиц `schools`, `staff`, `mo_departments`.
- Написать CRUD команды в `src-tauri/src/domain/identity.rs`.

### Фаза 2: Supabase Интеграция
- Создать зеркальные таблицы в облачном Supabase.
- Настроить RLS (Row Level Security) в Supabase, чтобы учителя из одной школы не видели данные другой школы.
- Написать в Rust модуль `src/infra/supabase_sync.rs` для обмена данными между локальной SQLite и облачным Supabase REST API.

### Фаза 3: Фронтенд (React)
- Расширить панель "Настройки" (которую мы недавно разрезали на секции).
- Добавить UI для управления "Школой" и "Сотрудниками" (добавление учителей, назначение ролей).
- Добавить статус-бар синхронизации с облаком (🟢 Синхронизировано / 🔴 Ошибка сети).
