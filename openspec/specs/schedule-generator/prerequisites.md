# Предварительные Требования (Prerequisites) для Генератора Расписания

Прежде чем мы сможем передать данные в математический солвер (CP-SAT), наше приложение должно собрать и структурировать колоссальный объем информации. 

Генератор не может работать без жестко типизированной матрицы входных данных. Ниже описано, какие модули необходимо разработать в приложении VectorWorkspace перед запуском алгоритма.

---

## 1. Модуль Инфраструктуры Школы (School Infrastructure)
*Необходимо расширить текущий домен `settings/identity`.*

### A. Управление Кабинетами (Rooms Management)
Пользовательский интерфейс и БД для создания аудиторий:
- `id`, `name` (например, "Кабинет №42")
- `capacity` (вместимость учеников)
- `room_type` (Лекционный, Химическая лаборатория, Лингафонный, Спортзал)
- `base_teacher_id` (какой учитель закреплен за кабинетом по умолчанию)

### B. Управление Учителями (Staff Profile)
- `availability_slots` — расписание доступности (например, Пн 1-6, Вт 3-5). Критично для приходящих учителей.
- `max_daily_lessons` — ограничение нагрузки в день.

---

## 2. Модуль Ученического Контингента (Student Cohorts)

### A. Управление Классами
- `id`, `name` (например, "8 А")
- `headcount` (количество учеников — нужно для сверки с вместимостью кабинетов).
- `shift` (смена: первая, вторая).

### B. Управление Подгруппами (Subgroups)
Возможность разделить класс на потоки.
- Правила деления (Например: "8 А делится на 2 группы для Английского языка и 2 группы для Физкультуры").

---

## 3. Модуль Рабочего Учебного Плана (Curriculum / Load Matrix)
*Самый сложный UI-блок. Именно здесь завуч распределяет нагрузку.*

Для каждого класса формируется матрица нагрузки:
- **Связка:** Класс `8 А` + Предмет `Алгебра` + Учитель `Иванов И.И.` + Количество часов `3`.
- **Флаги дисциплины:**
  - `is_double_lesson` (спаренный урок, например, Лабораторная).
  - `sanitary_weight` (вес сложности от 1 до 10 по СанПиН).
  - `required_room_type` (например, "только Спортзал").
- **Синхронные группы:** "Английский язык, 8 А" → Группа 1 (Учитель А), Группа 2 (Учитель Б). Занятия должны проходить **одновременно** в одном временном слоте.

---

## 4. Архитектура Backend'а (Интеграция Солвера)

На стороне Rust (`src-tauri/src`) необходимо подготовить инфраструктуру:
1. **Экстрактор Матрицы:** SQL-запросы, собирающие данные из кабинетов, учителей и планов в единый JSON/Struct.
2. **Интеграция CP-SAT:** 
   - Вызов C++ бинарника OR-Tools (например, через `std::process::Command`, передавая данные через JSON или Protobuf) или использование `ortools` crate (если поддерживается сборка).
3. **Парсер Решения:** Обработка результата (список `Assign[L][T][R] = 1`) и сохранение его в таблицу `timetable_slots`.

---

## Итог (Roadmap)
Попытка написать генератор сейчас — это строительство крыши без фундамента. 

**План действий:**
1. Спроектировать и реализовать БД и UI для Кабинетов и Классов.
2. Разработать сложный интерфейс Матрицы Нагрузки (Curriculum Builder), чтобы завуч мог связать Учителя, Предмет, Класс и Часы.
3. Только после того, как в БД появится реальная матрица нагрузки, писать математическую модель на OR-Tools.
