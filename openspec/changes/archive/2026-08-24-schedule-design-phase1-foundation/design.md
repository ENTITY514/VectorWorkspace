## Context

Модуль «Расписание» состоит из 380-строчного монолита `SchedulePage.tsx` с 10+ инлайн-компонентами. CSS-классы (`card`, `tabs`, `btn primary`, `badge ok`, `slider-row`, `timetable-grid`, `chip`) не определены в `styles.css` — UI визуально сломан. Design Sandbox (`DesignSandbox.tsx`) содержит корректные CSS-паттерны, но расписание их не использует. Все лейблы на английском. Дублирующий `Stat` компонент в `components/ui.tsx` и `shared/ui/Stat.tsx`.

## Goals / Non-Goals

**Goals:**
- Все лейблы, типы, статусыsolver на русском языке
- Определить все CSS-классы расписания в `styles.css` по стандарту Design System
- Разбить `SchedulePage.tsx` на 10 компонентов в `domains/schedule/ui/`
- Устранить дублирующий `Stat` компонент
- UI выглядит профессионально и согласованно с Design Sandbox

**Non-Goals:**
- Изменение функциональностиsolver
- Добавление новых фильтров (Фаза 2)
- Изменение data model
- Добавление новых вкладок или представлений

## Decisions

### D1: Локализация через маппинг в types.ts

**Решение:** Создать объекты-маппины (`ROOM_TYPE_LABELS`, `SHIFT_LABELS`, `STATUS_LABELS`, `FIELD_LABELS`) в `types.ts`, использовать в компонентах через `ROOM_TYPE_LABELS[roomType]`.

**Альтернативы:**
- i18n библиотека (react-intl, i18next) — избыточно для одноязычного приложения
- Локализация прямо в компонентах — дублирование, сложно поддерживать

**Обоснование:** Маппины просты, типобезопасны, централизованы. При необходимости добавить казахский — расширяем маппины.

### D2: CSS в глобальном стиле, не CSS-модули

**Решение:** Добавить все классы в `styles.css` (как это сделано для Design Sandbox и других компонентов).

**Альтернативы:**
- CSS-модули — не используются в проекте, нарушает консистентность
- Tailwind — импортирован, но нигде не используется

**Обоснование:** Проект использует глобальный CSS с BEM-подобнымNaming. Продолжаем существующий паттерн.

### D3: Компоненты в domains/schedule/ui/

**Решение:** Каждая вкладка — отдельный компонент в `domains/schedule/ui/`:

- `ScheduleDashboard.tsx`
- `TeachersTab.tsx`
- `ClassesTab.tsx`
- `RoomsTab.tsx`
- `SubjectsTab.tsx`
- `CurriculumTab.tsx`
- `WeightsTab.tsx`
- `GridTab.tsx`
- `LegacyTab.tsx`
- `ComparisonTab.tsx`

**Обоснование:** Каждый компонент <100 строк, тестируемый, переиспользуемый. Соответствует паттерну доменных UI (`tup/ui/`, `ktp/ui/`).

### D4: Удаление дубля Stat

**Решение:** Оставить `shared/ui/Stat.tsx`, удалить экспорт `Stat` из `components/ui.tsx`, обновить импорты в `Today.tsx`.

**Обоснование:** Единый источник истины, устраняет runtime-конфликты.

## Risks / Trade-offs

- **[Риск]** Разбиение монолита может сломать существующую логику → **Митигация:** Пошаговый рефакторинг, каждый компонент экспортируется отдельно, тестирование после каждого шага
- **[Риск]** Локализация может изменить поведение CSS (классы) → **Митигация:** CSS-классы остаются английскими (это технические имена), переводятся только лейблы и тексты
- **[Trade-off]** Маппины в types.ts vs i18n — проще, но менее гибко для мультиязычности → Приемлемо для одноязычного приложения
