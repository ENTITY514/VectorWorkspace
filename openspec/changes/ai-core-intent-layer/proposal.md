## Why

Опыт доработки расписания (`docs/schedule/06-lessons-v33-v53.md`) показал: педагоги формулируют задачи обычной речью,
а работу выполняют наши детерминированные алгоритмы. Модели нужно только понять просьбу, выбрать инструмент и параметры
и объяснить результат. То же верно для всего Vector: ТУП («сколько часов алгебры в 8 классе»), КТП («перенеси тему 5
на неделю позже»), КСП («добавь рефлексию в конец урока 12»), СОР/СОЧ («проверь веса СОЧ»), учебники
(«найди упражнение 45»), навигация («открой КСП 7А на завтра»).

В AI Core (`docs/08-mcp-core.md`) уже есть Tool Registry со схемами `schemars`, Hybrid Provider Gateway, карантин
`StagedArtifact` с «гильотиной инвариантов» и дифф перед сохранением. Но нет слоя, который превращает фразу
пользователя в вызов инструмента, особенно силами небольшой локальной модели (2–4B) или сервиса типизированного
выбора (например, Jev), а не большой генеративной модели.

Если делать такой слой отдельно в каждом модуле, получатся разные разметки сущностей, разные карточки подтверждения,
разные правила приватности. Нужен один платформенный слой.

## What Changes

- **Слой намерений AI Core** (Intent Layer): «фраза → вызов инструмента(ов) Tool Registry» с двухшаговым выбором
  (домен → команда), заполнением параметров, уточняющими вопросами и отказом «вне области».
- **Общая разметка сущностей** (без модели): учителя, классы, ученики, предметы, темы, уроки, четверти, дни, номера
  уроков, кабинеты, версии/документы; морфология русского (падежи ФИО), казахские формы, сокращения, прежние фамилии.
  Домены регистрируют свои типы сущностей и словари.
- **Тип провайдера «намерения»** в Hybrid Provider Gateway с адаптерами: локальная GGUF-модель с ограниченным выводом
  (llama.cpp), API типизированного выбора (Jev-подобный: Selection/Rating/Binary с уверенностью), энкодер-классификатор
  (ONNX), резервный парсер на правилах.
- **Единая карточка подтверждения** («Понял так») для всех изменяющих инструментов — поверх существующей «печати разума»
  (дифф) и карантина.
- **Объяснения результатов**: шаблоны инструментов + необязательный пересказ с проверкой «все числа и сущности — из
  результата инструмента».
- **Правило разделения**: слой намерений только выбирает инструменты; содержательная генерация (черновики КТП/КСП,
  формулировки) выполняется генеративными инструментами (`draft_ktp`, `draft_ksp`, …) через карантин и гильотину, как
  сейчас.
- **Приватность**: сущности размечаются локально; внешнему провайдеру — только фраза с метками; данные учеников —
  только метками; внешний провайдер — по согласию администратора.
- **Ресурсы**: модели докачиваются отдельно, лимит потоков, приоритет тяжёлых вычислений (солвер), таймауты с резервом.
- **Общий стенд оценки** (`ai-eval`): наборы фраз по доменам, метрики, пороги, правило «самая маленькая модель,
  прошедшая пороги».

## Capabilities

### New Capabilities
- `ai-intent-layer`: платформенный слой намерений AI Core.

### Modified Capabilities
- `ai-core` (docs/08-mcp-core.md): Tool Registry получает метаданные для слоя намерений (домен, признак «изменяет»,
  примеры фраз, шаблон объяснения); Provider Gateway — тип провайдера «намерения».

## Impact

- `Desktop/src-tauri/src/ai/intent/` — конвейер, разметка сущностей, пороги, журнал.
- `Desktop/src-tauri/src/ai/providers/intent/` — адаптеры `local_gguf`, `typed_api`, `encoder`, `rules`; sidecar llama.cpp;
  загрузчик моделей.
- `Desktop/src-tauri/src/ai/registry/` — расширение метаданных инструментов (макрос/атрибуты рядом с `schemars`).
- `Desktop/src/shared/ai/` — `AssistantPanel`, `UnderstoodCard`, `ExplanationView` (общие для всех доменов).
- `tools/ai-eval/` — стенд оценки; `docs/ai/intent-eval/<domain>/` — наборы.
- Первый домен-потребитель — `schedule-assistant`; затем КТП/КСП, ТУП, СОР/СОЧ, учебники, навигация.

## Non-goals

- Замена генеративных моделей для содержательных черновиков.
- Свободный чат «обо всём».
- Дообучение моделей (только сбор данных для него).
