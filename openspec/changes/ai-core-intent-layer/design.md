# Design: Слой намерений AI Core

## Место в AI Core

```
┌ VECTOR TAURI CORE ───────────────────────────────────────────────────────────────────────────┐
│  Фраза ─► [Intent Layer]                                                                     │
│             1 нормализация → 2 разметка сущностей → 3 выбор домена → 4 выбор команды           │
│             → 5 параметры → 6 проверка схемы/противоречий → 7 решение (выполнить / карточка /   │
│             уточнить / вне области)                                                           │
│                 │ провайдер «намерения» (модуль 4: Hybrid Provider Gateway)                   │
│                 ▼                                                                             │
│           [Tool Registry (модуль 2)] ──► инструменты-запросы/действия (детерминированный код)  │
│                                     └─► инструменты-генерация ──► карантин (модуль 5) ──►      │
│                                          гильотина инвариантов ──► дифф ──► сохранение          │
│  Результат ─► [Объяснение: шаблон инструмента ± пересказ с проверкой чисел] ─► пользователь     │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 1. Метаданные инструментов (расширение Tool Registry)

Каждый инструмент, доступный слою намерений, помечается рядом с его схемой `schemars`:

```rust
#[intent_tool(
    domain = "schedule",
    mutates = true,              // изменяет данные → карточка подтверждения
    generative = false,          // генеративный → только через карантин
    examples = ["Мельникову 3 дня и до 5-го урока"],
    explain = "templates/schedule/set_teacher_work_mode.{ru,kk}.md",
    entity_slots = ["teacher"],  // параметры, значения которых берутся только из разметки
)]
struct SetTeacherWorkMode { /* … */ }
```

- Тест реестра: у каждого инструмента с `#[intent_tool]` есть ≥ 3 примера, шаблоны ru/kk, корректная схема.
- Инструменты без атрибута слою намерений не видны.

## 2. Разметка сущностей (общая)

- **Реестр типов сущностей**: ядро предоставляет общие типы (учитель, класс, ученик, предмет, день, номер урока, время,
  четверть, дата, кабинет); домен регистрирует свои (тема ТУП/КТП, урок КСП, СОР/СОЧ, версия расписания, упражнение).
- **Словари** строятся из SQLite при открытии рабочего пространства и обновляются по событиям изменения данных.
- **Нормализация**: регистр, ё/е, числительные («пятого» → 5), «до/после/не позже N-го», даты («на завтра», «в следующую
  среду»), раскладка клавиатуры.
- **Морфология**: падежные формы ФИО (ru), казахские окончания; прежние фамилии; инициалы; «Ольга Викторовна».
- **Неоднозначность → уточнение**, никогда не выбор наугад (пример: «Мельникову» → Мельников П.В. / Мельникова Л.Р.).
- Результат — фраза с метками (`<TEACHER:T17>`) и список кандидатов для каждой метки.

## 3. Двухшаговый выбор

1. **Домен**: если текущий экран однозначно задаёт домен (открыт редактор КСП) — домен берётся из контекста; иначе
   провайдер выбирает из ~8 доменов (расписание, ТУП, КТП, КСП, СОР/СОЧ, учебники, навигация, настройки).
2. **Команда** внутри домена: выбор из ≤ 40 команд домена.
3. **Параметры**: сущностные слоты — только из кандидатов разметки; прочие — по схеме (перечисления, числа с диапазонами).

Одна фраза MAY дать несколько команд (одного или разных доменов) → один набор изменений, одна карточка.

## 4. Провайдер «намерения»

```rust
trait IntentProvider {
    fn select(&self, ctx: &IntentContext, options: &[Choice]) -> Result<Vec<Scored<ChoiceId>>>;
    fn fill(&self, ctx: &IntentContext, schema: &Schema, candidates: &SlotCandidates) -> Result<Scored<Value>>;
    fn binary(&self, ctx: &IntentContext, question: &str) -> Result<Scored<bool>>;   // «нужно уточнение?»
    fn paraphrase(&self, draft: &ExplanationDraft, q: Option<&str>) -> Option<Result<String>>;
    fn capabilities(&self) -> ProviderCaps; // local/remote, languages, paraphrase, max_options
}
```

| Адаптер | select / fill / binary | paraphrase | Где | Примечания |
|---|---|---|---|---|
| `local_gguf` | генерация с грамматикой GBNF/JSON-схемой; уверенность — log-prob выбранных токенов или согласие 3 прогонов | да | локально | размер 1–4B, Q4; казахский проверять |
| `typed_api` (напр. Jev) | Selection / Rating / Binary нативно, уверенность из ответа | нет | облако | только обезличенный вход; закрытая лицензия; язык и размер не раскрыты |
| `encoder` | классификатор намерений + разметка слотов (ONNX) | нет | локально | самый быстрый, нужен обучающий набор |
| `rules` | ключевые слова + шаблоны | нет | локально | всегда доступен, резерв |

Провайдеры регистрируются в Hybrid Provider Gateway; к ним применяется существующий Circuit Breaker. Выбор — настройка
рабочего пространства; допустима комбинация (например, `encoder` для выбора домена + `local_gguf` для параметров).

## 5. Решение и подтверждение

- Пороги уверенности на выбор домена, команды и каждый параметр; ниже порога → `clarify` с 2–3 вариантами.
- Запросы (`mutates=false`) выполняются сразу.
- Изменяющие команды → **карточка «Понял так»**: человекочитаемое описание параметров, «Верно / Исправить / Отмена»,
  доменные действия (например, «Оценить цену» в расписании). После «Верно» изменения проходят обычный путь домена,
  включая дифф («печать разума») и атомарную транзакцию.
- Генеративные инструменты (`generative=true`) вызываются только через карантин `StagedArtifact` и гильотину; слой
  намерений передаёт им параметры, но не пишет содержание сам.

## 6. Объяснения

- Шаблон инструмента (ru/kk) заполняется полями результата — основной путь, работает без модели.
- Пересказ (если провайдер умеет): проверка «все числа и сущности текста ∈ результат инструмента»; при нарушении —
  шаблон и запись в журнал.
- Ссылка на источник (отчёт, документ, проверка) под каждым объяснением.

## 7. Приватность

- Разметка всегда локальна; наружу — фраза с метками и список вариантов без персональных данных.
- Ученики, ДО, инклюзия, оценки — только метками.
- Внешний провайдер включает администратор; в настройках — перечень передаваемых полей; журнал запросов наружу.

## 8. Ресурсы школьного ПК

- Модели не входят в установщик; загрузка по кнопке с проверкой контрольной суммы.
- Лимит потоков (по умолчанию ½ ядер); **приоритет тяжёлых вычислений**: во время солвера расписания, OCR, импорта —
  пауза или один поток.
- Таймаут (по умолчанию 20 с) → резерв `rules` + предложение открыть форму вручную.
- Эталонный ПК для оценки: i3 / 8 ГБ ОЗУ / без GPU.

## 9. Стенд оценки `ai-eval`

- Наборы по доменам: `docs/ai/intent-eval/<domain>/commands.jsonl`, `explanations.jsonl`
  (для расписания — `docs/schedule/assistant-eval/`).
- Метрики: точность домена, команды, параметров; уточнения на неполных фразах; ложные выполнения изменяющих команд;
  `out_of_scope`; время p95 на эталонном ПК; совпадение чисел в пересказе.
- Пороги по умолчанию: команда ≥ 95 %, параметры ≥ 90 %, уточнения ≥ 90 %, ложные выполнения = 0,
  вне области ≥ 95 %, p95 ≤ 5 с (команда) / ≤ 15 с (пересказ), числа в пересказе 100 %.
- Правило выбора: **самый маленький провайдер, прошедший пороги на всех подключённых доменах**; результаты — в
  `docs/ai/intent-eval/results/`.

## 10. Журнал

Локально: фраза (обезличенная копия), домен, команда, уверенность, решение, исправления пользователя. Экспорт — вручную,
для пополнения наборов оценки и возможного дообучения.

## Порядок внедрения

1. Ядро: метаданные реестра, разметка сущностей, провайдеры `rules` + один локальный, карточка, шаблоны, стенд.
2. Домен «Расписание» (`schedule-assistant`) — этап запросов, затем изменений.
3. Навигация и КСП/КТП (запросы и простые правки), затем ТУП, СОР/СОЧ, учебники.
