# 06. Уроки реального расписания 2026–2027 (V33 → V53) и план развития

Документ фиксирует, что показала работа над реальным расписанием школы (версии V33–V53, сентябрь 2026),
и связывает выводы с пятью изменениями OpenSpec. Это вход для продуктового планирования; детали —
в самих изменениях (`openspec/changes/…`).

## Что произошло

- Утверждённое расписание (V33, правка завуча V33(1)) пришлось дорабатывать пять раз: директору нужны
  3 рабочих дня, классный руководитель ждал первого урока, ученица на инклюзии сидела в окнах и до 7-го
  урока, у учителя-совместителя было два окна подряд, учитель музыки приходил ради одного урока.
- Часть доработок сделана упрощённым скриптом вне основной модели: итог «0 нарушений СанПиН» оказался
  неверным (физика два дня подряд, большой класс в малом зале, запрещённый урок математики).
- Итоговая V53: окон у учителей 95 → 82, дней «ради одного урока» 13 → 5, СанПиН на 2,6 % лучше исходной
  доработки, все требования выполнены; сдвинуто 88 уроков из 519 (совпадение 83 %).

## Выводы → изменения

| # | Вывод | Изменение OpenSpec |
|---|-------|--------------------|
| 1 | Ключевые требования — свойства ролей и людей, которых нет в модели данных: классный руководитель, директор, совместитель, ученик на инклюзии, размер класса ↔ зал, парные предметы, пожелание учителя | `schedule-school-profile` |
| 2 | Пользователь мыслит приоритетами («СанПиН важнее окон», «ученик важнее моих обменов»), а не весами; каждое правило должно быть явно «обязательно / по возможности / выключено» | `schedule-rules-priorities` |
| 3 | После утверждения нужна доработка с минимумом изменений: база, закрепления, доказанный минимум сдвигов, досчёт, импорт правок завуча, ручные перестановки | `schedule-revision-mode` |
| 4 | Самые ценные ответы — «цена требования» и понятная причина невыполнимости («большой зал в Пн/Ср/Пт занят началкой») | `schedule-what-if` |
| 5 | Каждый участник смотрит своим взглядом (учитель, классный руководитель, ребёнок, ученик на инклюзии, завуч, директор); версии надо сравнивать и помечать статусом; проверка должна подтверждать каждое требование, а не только «ограничение добавлено» | `schedule-compare-and-reports` |

| 6 | Педагоги говорят обычной речью; модель нужна только чтобы выбрать инструмент и параметры и объяснить результат — расчёт, проверки и сравнение остаются нашими алгоритмами | `ai-core-intent-layer` (платформа) + `schedule-assistant` (домен) |

## Порядок внедрения

```
schedule-school-profile ──► schedule-rules-priorities ──► schedule-revision-mode ──► schedule-what-if
                                     │                                                    ▲
                                     └──────────────► schedule-compare-and-reports ───────┘
```

1. **Профиль школы** — без него нечего приоритизировать.
2. **Каталог правил** — заменяет 6 ползунков весов; на него опираются остальные.
3. **Сравнение и отчёты** — нужны для оценки любого результата (можно параллельно с п. 2).
4. **Режим доработки** — самый частый сценарий после сентября.
5. **«Что если»** — строится поверх режима доработки и сравнения.
6. **Слой намерений AI Core** — можно вести параллельно с п. 1–5 (ядро, провайдеры, стенд оценки); домен «Расписание»
   (`schedule-assistant`) подключается поэтапно по мере готовности команд: запросы → изменения → доработка.
   Набор оценки домена уже собран: `docs/schedule/assistant-eval/`.

## Эталонные сценарии для приёмки (из реального кейса)

Каждое изменение содержит сценарии; ниже — сквозные, на которых проверяется весь набор:

1. Директор-учитель физкультуры: ровно 3 рабочих дня по 3 урока, уроки 1–5. Система находит, что в
   третий день два окна подряд неизбежны (большой зал занят закреплённой сеткой начальной школы), и
   объясняет это, а не молчит и не падает.
2. Классный руководитель приходит к 1-му уроку: ожидание до первого урока считается окном; отчёт
   показывает «окна с 1-го урока» по всем классным руководителям.
3. Ученица на инклюзии посещает часть уроков класса: каждый день с 1-го урока, не позже 6-го,
   не больше 1 окна в день и 3 в неделю; система сама выбирает, на какие 2 из 4 уроков казахского она ходит.
4. Доработка утверждённой версии: доказанный минимум сдвигов (10 уроков) сохраняется отдельной версией,
   затем досчёт улучшает окна ценой ещё 9 сдвигов; пользователь сравнивает обе и выбирает.
5. «Что если»: большой зал для маленьких классов → +14 баллов СанПиН, 7 сдвигов, 2 новых дня ради одного
   урока; пользователь отказывается до пересчёта основной версии.
