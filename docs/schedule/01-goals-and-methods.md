# 01. Цели, Критерии и Методы — Почему исключительно CP-SAT

## 1.1 Абсолютная цель (формальная постановка)

Дано:
- Множество учителей `U` (|U| ≤ 80), классов `C` (|C| ≤ 40), кабинетов `R` (|R| ≤ 50), предметов `S`, временных слотов `T = D × P` (|D|=6, |P|=7-8, |T|≤48).
- Матрица нагрузки `L: C × S → (teacher, hoursPerWeek, flags)` — часы из ТУП, уже распределённые завучем.
- Матрица доступности `A: U × T → {0,1}`.
- Типы кабинетов `RT`, закрепления `baseRoom: U → R ∪ {null}`.

Найти отображение `assign: Instance → T × R` такое что:
- Все Hard-ограничения (§03) выполнены (0 нарушений).
- Взвешенная сумма штрафов Soft-ограничений минимальна.
- Время поиска ≤ 60 сек на типовой школе, ≤ 180 сек на крупной (60 классов).
- При INFEASIBLE — вернуть диагностику минимального конфликтного ядра, а не падение.

Коллизия = любое нарушение Hard. Требование: **0 коллизий** в любом `OPTIMAL`/`FEASIBLE` решении.

## 1.2 Критерии приёмки (Acceptance Criteria)

| ID | Критерий | Измерение | Порог |
|----|----------|-----------|-------|
| AC-01 | Отсутствие Hard-нарушений | Автовалидатор `validate_hard()` на результате | 0 |
| AC-02 | Время решения (медиана, 3 прогона) на синтетике 30×40×35×30 слотов | `solver_wall_ms` | ≤ 60 000 мс |
| AC-03 | Оптимальность | `gap = (best - bound)/best` при лимите времени | ≤ 5% или `OPTIMAL` |
| AC-04 | Детерминизм | 5 прогонов с одним `seed` → идентичный JSON | 100% |
| AC-05 | INFEASIBLE-диагностика | При искусственном конфликте (10 уроков в 8 слотов) — статус + список конфликтующих сущностей | Обязателен |
| AC-06 | Расщепление | Для `requires_split` — 2 подгруппы в один `T`, разные `teacher` и `room` | 100% тестов |
| AC-07 | Спецкабинеты | Предмет с `required_room_type != null` → только пул `R_type` | 0 нарушений |
| AC-08 | СанПиН-вес | Суммарный дневной вес класса отклоняется от параболы не более чем на `tolerance` при `weight>0` | Штраф измерим |
| AC-09 | Управляемость весов | Установка любого `Weights.* = 0` полностью отключает соответствующий Soft без пересборки | Проверка |
| AC-10 | Изоляция UI | Вкладка «Расписание» не импортирует `tup/ktp` напрямую, только `schedule`-API | Линт-правило |

## 1.3 Почему не эвристики, не GA, не полный перебор

| Подход | Сложность на 30×40 | Гарантия Hard | Сходимость | Почему отклонён |
|--------|-------------------|---------------|------------|-----------------|
| **Brute Force** | `|T|^(|L|) ≈ 30^600` — больше атомов во Вселенной | Теоретически да | Никогда | Невозможен |
| **Жадный + бэктрекинг (вручную `for/if`)** | Экспонента, застревает в локальных минимумах | Нет — «дыры» | Случайна | Неуправляемый код, непроверяем |
| **Genetic Algorithm** | `O(pop×gen×eval)` — быстро, но | Нарушает Hard, требует штрафов-костылей | Не гарантирует 0 коллизий | Требует настройки мутаций, нестабилен на INFEASIBLE |
| **ILP (CBC/Gurobi)** | Сильный на линейных моделях | Да | Хороша, но хуже на логике/дизъюнкциях | Дорогие лицензии (Gurobi), слабее на булевой логике |
| **CP-SAT (OR-Tools, Lazy Clause Generation + Propagation)** | `O(branch×propagate)` — лучший на дизъюнктах | Да (декларативно) | Доказуемая оптимальность | **Выбран** |

### Формальное обоснование CP-SAT

1. **Декларативность**: описываем *что* нельзя (`.Add(sum <= 1)`), а не *как* искать. Солвер сам применяет propagation, clause learning, параллельный поиск.
2. **Разделение Hard/Soft**: Hard = `Add`/`AddAllDifferent`/`AddExactlyOne`; Soft = булевы индикаторы нарушения + коэффициент в `Minimize`. Вес `0` → индикатор не создаётся, ветка исчезает.
3. **INFEASIBLE-анализ**: CP-SAT возвращает `INFEASIBLE` с возможностью извлечь `Assumptions` / `Conflict` (через `AddAssumptions` + `SolutionHint`), в отличие от GA где «не нашёл» ≠ «не существует».
4. **Производительность**: на STP 30×40×30 слотов CP-SAT (OR-Tools 9.10) решает за 5-45 сек на 8 ядрах (параллельный `num_search_workers=8`), GA требует > 10 мин для сопоставимого качества.
5. **Лицензия**: Apache 2.0, встраивается в Tauri без серверной зависимости, в отличие от Gurobi/CPLEX.
6. **Зрелость**: используется в Google, Air France, производстве — доказан на задачах с 1M+ переменных.

**Вывод**: единственный метод, удовлетворяющий требованию «0 коллизий + минимизация штрафов + диагностика INFEASIBLE + offline + ≤60 сек» без компромиссов — **OR-Tools CP-SAT**.

## 1.4 Методология: Переменные → Ограничения → Целевая функция

Трёхфазная схема (см. §03 детально):

```
Фаза A: Переменные
  x[c,s,g,teacher,room,day,slot] ∈ {0,1}  // g=0 для обычных, g∈{0,1} для split
  или OptionalInterval для double-уроков

Фаза B: Hard (Add, AddExactlyOne, AddAtMostOne)
  - Сингулярность учителя/класса/кабинета
  - Availability (x=0 вне матрицы)
  - Расщепление (синхронность подгрупп)
  - Спецкабинет (x=0 вне пула)

Фаза C: Soft (штрафные индикаторы → Minimize)
  penalty = w1·windows + w2·room_displacement + w3·sanpin_deviation + w4·alternation
  Objective = Minimize(penalty)
  w_i = Weights.* (0 = отключено, 1..1000 = интенсивность)
```

Масштабируемость: веса — динамические, меняются ползунком в UI без перекомпиляции модели (пересобирается только objective).

## 1.5 Ограничения метода (честно)

- CP-SAT — NP-Hard, worst-case экспонента. На школе 60 классов × 50 учителей может потребовать > 180 сек → предусмотрен `time_limit_sec` + возврат лучшего `FEASIBLE` (не `OPTIMAL`) с `gap`.
- Требуется Python-runtime (встраиваем `python-embed` или требуем системный Python 3.10+ с `ortools`).
- Парабола СанПиН — Soft, не Hard: при экстремальной нагрузке (8 уроков/день) идеальная парабола недостижима → штраф неизбежен, но Hard не нарушается.

## 1.6 Связь с нормативами РК

- **СанПиН (ҚР ДСМ-76)**: веса сложности предметов (матем 10, физ-ра 2, и т.д.) берутся из Приложения 2, парабола — методика распределения по дням (п. 37-42). Реализуется как Soft с настраиваемым весом.
- **ТУП**: часы/нед по предметам задают `hoursPerWeek` в Curriculum Matrix; валидируются против `tup_documents.hours`.
- **Смены**: `class.shift = 1|2` → `T` ограничивается `Add(x=0)` для чужой смены (Hard).

## 1.7 Что будет считаться провалом планирования

- Выбор GA/эвристики вместо CP-SAT без математического обоснования.
- Отсутствие INFEASIBLE-диагностики.
- Модель где вес `0` не отключает ограничение (нарушение §1.2 AC-09).
