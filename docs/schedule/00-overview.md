## 0.2 Абсолютная цель (в одну фразу)

Спроектировать и реализовать **производственную систему** автоматической генерации расписания класса NP-Hard, которая за ≤ 60 секунд на типовой школе (30 классов × 40 учителей × 35 кабинетов × 30 слотов/нед) выдаёт **0 коллизий** по Hard-ограничениям и минимизирует взвешенный штраф по Soft-ограничениям, полностью изолирована в десктопе (Tauri+SQLite+OR-Tools) и управляется из React-UI.

## 0.3 Границы системы (Scope)

### В Scope (MVP → V1)
- Справочники: учителя (availability matrix, baseRoom), классы (headcount, shift, подгруппы), кабинеты (type, capacity), предметы (sanitary_weight, required_room_type, requires_split, is_double).
- Матрица нагрузки (Curriculum Matrix): связка `Класс × Предмет × Учитель × Часы/нед` — единственный вход для солвера.
- Ядро CP-SAT (Python, OR-Tools 9.10+): Hard (сингулярность, фиксированные слоты, расщепление, специфика кабинета) и Soft (окна, изгнание из кабинета, СанПиН-парабола, чередование).
- JSON-контракт с версионированием, валидация на обеих сторонах.
- UI-вкладка «Расписание» (изолированная): CRUD справочников, ползунки весов, грид-матрица, фильтры, подсветка окон/коллизий, экспорт.
- Диагностика INFEASIBLE с указанием минимального конфликтного ядра (IIS-подобный отчёт).

### Вне Scope (Non-Goals) для MVP
- Облачная синхронизация расписания (только локальный SQLite; синхронизация — фаза 10 общего roadmap).
- Автоматический учёт замен/больничных в реальном времени (ручной пересчёт).
- Генетические/эвристические альтернативы солверу.
- Мобильное приложение, Kundelik-API (только экспорт CSV/XLSX).

## 0.4 Глоссарий

| Термин | Определение |
|--------|-------------|
| **Слот** `T = (day, period)` | Дискретный временной интервал: `day ∈ [0..5]` (Пн-Сб), `period ∈ [0..7]` (1-8 урок). Всего 36-48 слотов/нед. |
| **Lesson Instance** | Атомарная единица расписания: `Класс × Предмет × Учитель × Группа × Кабинет × T`. Для `requires_split` — 2 instance одновременно. |
| **Availability Matrix** | `teacher_id × T → bool` — где учитель физически может вести. `false` = жёсткий запрет. |
| **BaseRoom** | Закреплённый кабинет учителя (мягкое предпочтение). |
| **СанПиН-вес** | Балл сложности предмета 1..10 по Приказу № ҚР ДСМ-76 (математика/физика высокие, физкультура низкая). |
| **Парабола СанПиН** | Идеальное распределение суммы весов по дням: пик Вт-Ср, спад Пн/Сб. |
| **Окно** | Пустой слот между первым и последним уроком учителя в день. |
| **Расщепление** | `requires_split=true` → класс делится на 2 подгруппы, требуют 2 учителя+2 кабинета в один `T`. |
| **INFEASIBLE** | Статус CP-SAT: система Hard-ограничений противоречива, решения нет. |

## 0.5 Принципы проектирования (наследуются из `docs/01-manifest.md`)

1. **Code-Enforced Invariants** — СанПиН-веса, вместимость, смены кодируются в Rust newtype + CHECK-ограничениях SQLite, а не в комментариях.
2. **Offline-First** — расписание считается локально; OR-Tools не требует интернета; БД — SQLite WAL.
3. **Non-Blocking Actor Core** — солвер — отдельный `tokio::process::Child`, не блокирует Tauri UI; прогресс через события.
4. **Zero-Trust Solver** — Python никогда не пишет в БД напрямую; только возвращает JSON, который Rust валидирует и атомарно коммитит.

```
VectorWorkspace (Tauri v2 + React)
├── docs/09-database-schema.md  ─┐
├── docs/14-data-types...md      ├── существующие домены (ТУП/КТП/КСП/СОР)

└── Desktop/src/                 ─┘
         │
         └── НОВЫЙ ИЗОЛИРОВАННЫЙ КОНТУР schedule/
              ├── Rust: domain/schedule, db/schedule, commands/schedule
              ├── Python: solver/ (OR-Tools) — sidecar-процесс

```

Изоляция: вкладка «Расписание» не импортирует `ktp/`, `tup/` напрямую, только через `schedule`-API. Любая регрессия в расписании не ломает КТП.
