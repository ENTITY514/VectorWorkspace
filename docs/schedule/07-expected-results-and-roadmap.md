# 07. Ожидаемый Результат, Метрики и Поэтапный Roadmap

## 7.1 Что считается «Готово» (Definition of Done)

### Продуктовый результат

1. **Десктоп-приложение Vector** с новой вкладкой «Расписание» в `MainLayout` (рядом с КТП/КСП).
2. **4 справочника**: учителя (с матрицей доступности), классы (с подгруппами), кабинеты (тип/вместимость), предметы (вес СанПиН, спецкабинет, split).
3. **Матрица нагрузки** (Curriculum) — завуч распределяет часы за 5 минут на 30 классов.
4. **Конфигуратор весов** — 6 ползунков (окна, кабинет, СанПиН, чередование, миграция, баланс), вес `0` мгновенно отключает.
5. **Кнопка «Сгенерировать»** → за 5-60 сек `OPTIMAL`/`FEASIBLE` расписание с `0` Hard-нарушений, видимое в **Grid-матрице** (фильтры по классу/учителю/кабинету, подсветка окон/параболы).
6. **INFEASIBLE-диагностика**: вместо падения — карточка «Учитель Иванов: 22ч > 18 слотов» с кликабельными ссылками.
7. **Экспорт** XLSX/CSV (по классам и по учителям) для загрузки в Күнделік/печать.
8. **Производительность**: типовая школа 30×40 — ≤60 сек, 60 классов — ≤180 сек, gap ≤5%.

### Технический результат

- Миграция `0010_schedule.sql` накатывается с нуля и повторно.
- `cargo test` + `pytest` + `vitest` — зелёные, покрытие ≥ 80/85/70.
- `SolverHost` — изолированный Python, не блокирует UI, логи в `stderr`.
- JSON-контракт `schema_version=1` валидируется `schemars` + `pydantic`.
- Линт `no-restricted-imports` — `schedule` не импортирует `tup/ktp`.

## 7.2 Метрики успеха (измеримые)

| Метрика | Цель | Как измерить |
|---------|------|--------------|
| Hard-нарушения в `OPTIMAL` | 0 | `validate_hard()` на выходе |
| Время типовой школы (30×40) | p50 ≤ 30с, p95 ≤ 60с | `solver_stats.wall_ms` (3 прогона) |
| Оптимальность | `OPTIMAL` или `gap ≤5%` | `gap_percent` |
| INFEASIBLE-диагностика | 100% случаев с `reason` + `entities` | Тесты §06.4 |
| Расщепление (split) | 100% параллельно, разные room/teacher | `test_sanity_split_parallel` |
| Управляемость весов | `weight=0` отключает, `1000` максимизирует | Тесты §06.3 |
| UX: время заполнения данных | ≤ 10 мин на типовую школу (с демо-данными) | Ручной замер |
| Экспорт | XLSX открывается в Excel/LibreOffice | Ручной тест |

## 7.3 Ожидаемый эффект для школы (РК)

- **Экономия времени завуча**: 2-3 дня ручной работы → 10 минут настройки + 1 минута генерации.
- **Соответствие СанПиН**: автоматическая парабола Вт-Ср, лимиты нагрузки, веса сложности — снижение жалоб родителей.
- **0 коллизий**: учитель/класс/кабинет никогда не двоится — система физически не позволяет сохранить конфликт.
- **Гибкость**: приходящие учителя, смены, спецкабинеты — без «костылей», всё Hard/Soft.

## 7.4 Roadmap — 5 фаз (внутри общего roadmap Vector)

> Каждая фаза — отдельный PR, мержится только после `cargo test` + `pytest` зелёных.

### Фаза 1 — Фундамент данных (1 неделя)

**Цель**: БД + CRUD справочников + матрица доступности.

- Миграция `0010_schedule.sql` (все `schedule_*`).
- Rust: `domain/schedule/model.rs`, `validation.rs`, `db/schedule/*` (CRUD).
- Tauri-команды: `schedule_get_state`, `upsert_teacher/room/class/subject`, `set_curriculum`, `set_weights`.
- Тесты: §06.2 (unit, DDL).

**Критерий**: `cargo test` зелёный, `Settings → Расписание` показывает пустые справочники.

### Фаза 2 — Python-ядро и JSON-контракт (1 неделя)

- `solver/schema.py` (pydantic), `solver/engine.py` (переменные + H1..H10), `solver/__main__.py`.
- Rust: `infra/solver_host.rs` + `commands/schedule_generate` (stdin/stdout).
- JSON Schema `schema_version=1`, валидация обеих сторон.
- Тесты: §06.3.1-06.3.4 (Hard), `test_solver_host_success`.

**Критерий**: `pytest` зелёный на micro/typical, Rust может вызвать Python и получить `OPTIMAL` на 1 классе.

### Фаза 3 — Soft-ограничения и целевая (1 неделя)

- `solver/constraints/soft.py` (S1..S6 + `Minimize`).
- Веса `Weights` в SQLite + API `schedule_set_weights`.
- Тесты: §06.3.5-06.3.8 (Soft, weight=0), парабола, чередование.

**Критерий**: при `window=1000` окон 0, при `window=0` окна игнорируются; аналогично для остальных.

### Фаза 4 — UI (2 недели)

- `domains/schedule/` — все 5 экранов (§05): Dashboard, DataManagement (4 таба), CurriculumMatrix, ConstraintsConfigurator, TimetableGrid.
- Интеграция: `SchedulePage` в `App.tsx` (`View="schedule"`), `scheduleApi.ts`, `useScheduleProgress`.
- Экспорт XLSX/CSV (`schedule_export`).
- Тесты: `vitest` для компонентов, E2E сценарий (§06.5).

**Критерий**: пользователь может без консоли пройти путь «Справочники → Нагрузка → Веса → Генерация → Грид → Экспорт».

### Фаза 5 — Полировка, INFEASIBLE, нагрузка (1 неделя)

- Диагностика `infeasible_core` (§03.5) + Dashboard-карточка.
- Нагрузочные тесты (§06.7) + оптимизации (предфильтр, `num_search_workers`).
- Демо-данные (школа 20 классов) + документация пользователя.
- Покрытие ≥80/85/70, `cargo tarpaulin` + `pytest --cov`.

**Критерий**: все чек-листы §06.9 зелёные, типовая школа ≤60 сек на CI.

**Итого**: 6 недель от старта до `V1` (при 1 разработчике full-time, 3 недели при 2).

## 7.5 Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| CP-SAT >60с на 60 классах | Средняя | Высокое | `time_limit` + `FEASIBLE` с gap, `SolutionHint` warm-start, `num_workers=8` |
| Python не установлен у пользователя | Высокая | Среднее | Embed `python-embed` в дистрибутив Tauri, fallback диалог «Установите Python» |
| СанПиН-парабола недостижима при 8 уроках/день | Средняя | Низкое | Soft, не Hard; вес регулируется, предупреждение в Dashboard |
| INFEASIBLE без понятной диагностики | Низкая | Высокое | Эвристика §03.5 + UI-карточка с сущностями, тест §06.4 |
| UI-изоляция нарушена (импорт tup) | Низкая | Среднее | Линт `no-restricted-imports`, code-review |
