# 12. Реестр утверждённых решений (ADR)

## I. Стратегия исполнения (реализация)

| Решение | Директива |
|---------|-----------|
| Порядок ковки | **Строго по контурам, без перескакивания:** 1) Нормативный базис (ТУП) → 2) Календарь (КТП) → 3) Поурочные планы (КСП) → 4) Оценивание (СОР/СОЧ) → 5) База знаний учебников → 6) MCP-сервер (финальная корона). |
| Искоренение старой схемы | Существующая «упрощённая» схема (таблицы `lessons/tasks/ksp/sor/calendar`) **выкорчёвывается целиком и немедленно**. Никаких поэтапных миграций. Применяется производственный DDL из документа 09 полностью. |
| Асинхронное ядро | Переход с `rusqlite` (sync, `Mutex<Connection>`) на **`sqlx::SqlitePool` (async, tokio)** обязателен. Блокировка главного потока Tauri недопустима (Non-Blocking Actor Core). |

## II. Методические инварианты (дисциплина планирования)

| Решение | Директива |
|---------|-----------|
| Интервал оценивания FR-2.2 | Закон одного урока до СОЧ непреложен. При нескольких СОР в четверти буферный урок отсчитывается **строго от последнего СОР перед СОЧ**. Предыдущие оценивания закон не отменяют. |
| Хронометраж КСП | Гибкость = осознанный выбор, не небрежность. Система позволяет учителю задать **эталон длительности урока** (например, 40 или 45 минут). Как только эталон установлен — сумма этапов обязана сойтись с ним **точно (Σ == эталон)**, без плавающих диапазонов. |

## III. Контур оцифровки (зрение архитектуры)

| Решение | Директива |
|---------|-----------|
| Природа PDF | Закладывается **гибридный пайплайн немедленно**: (а) молниеносное извлечение чистого текстового слоя, если он есть; (б) фоновый OCR для отсканированных страниц. Ожидать худшее качество исходников. |
| Ограничение по классам | **Основное поле боя:** 7–9 классы (контентная фокусировка). Но архитектура БД обязана поддерживать **все уровни 1–12 классы без слепых зон** (умолчания/расширение). |
| Текущий преподавательский состав | Ведение: 8–10 классы, предметы алгебра/геометрия. Проект масштабируется на всех учителей и все классы/предметы в будущем. |

## IV. Протокол ИИ (MCP и AI)

| Решение | Директива |
|---------|-----------|
| Локализация MCP | Сервер встраивается **непосредственно в Tauri-ядро на Rust**. Внешние отдельные процессы для сервера запрещены — приложение самодостаточная крепость. |
| Владение провайдерами | Диспетчер обязан: (а) **самостоятельно порождать и контролировать процесс OpenCode через stdio**; (б) быть открытым для входящих соединений внешних агентов (SSE/API). |
| Хранилище секретов | Инфраструктура **OS Keyring** (Windows Credential Manager) реализуется **немедленно, до наличия реальных ключей**. Секреты в конфиг-файлах запрещены. |
| Приоритет интеграции | В идеале работа идёт **из приложения → приложение обращается к OpenCode и работает через него**. Если технически невозможно — реализуется отдельный MCP-сервер как резервный путь. |

|---------|-----------|

## VI. Директивы уточнения (фиксация 2)

### 6.1. Предметная модель ТУП — изоляция дисциплин
- Коды целей (например, `8.4.1.3`) **не глобально уникальны**: в алгебре и геометрии один код означает разное.
- `LearningObjective` жёстко привязана к `TupDocumentId`; сам `TupDocument` содержит `subject_id`.
- **Не дублировать** `subject_id` в таблице целей — схема БД уже защищена.
- Rust-код при выборке целей (например, для КСП) обязан делать **JOIN через документ** и **строго фильтровать по предмету**. Смешивание целей разных дисциплин недопустимо.

### 6.2. Запуск OpenCode — железная хватка (Stdio)
- Приложение — повелитель, локальный агент — послушный механизм.
- Tauri-ядро на Rust **порождает дочерний процесс OpenCode CLI напрямую** (`std::process::Command`).
- Связь — **исключительно через stdio** (stdin/stdout) по протоколу **JSON-RPC (MCP)**. Внешние порты и обособленные серверы запрещены.
- Код перехватывает stdin/stdout процесса. При зависании агента ядро **безжалостно убивает процесс (kill) и запускает заново**. Абсолютный контроль.

### 6.3. Хранилище учебников — ответственность творца
- Система не рождается с вложенными знаниями; база не заполняет саму себя.
- Исходные PDF-файлы находятся в физическом распоряжении пользователя.
- Индексатор в Rust **не зависит от жёстко прописанных путей**.
- Конвейер: учитель указывает путь к любому PDF-файлу на диске → система страница за страницей извлекает текстовый слой и переводит математику в LaTeX.

### 6.4. Источники ТУП — ковка из сырья
- Нормативы из локальной директории `Materials` (`.xlsx`) — сырая руда.
- Парсер преобразует эти файлы в жёсткую DDL-схему.
- Обязан **безошибочно** обрабатывать программы 7–9 классов.
- Обязан **выдерживать структуру нормативов для 10 классов** с учётом требований к объединению и специфике учебных часов.
- Если парсер ломается на неровной строке Excel — переписать, пока не станет работать безупречно.

### 6.5. Язык интерфейса — фокус и концентрация
- Базовый UI и логика на старте — **только русский (RU)**. Фокус на математических и архитектурных инвариантах.
- На уровне React **ни одна строка текста не «зашивается» жёстко** — используется **архитектура локализации (i18n) с первого дня**.
- Внедрение казахского языка (KK) после стабилизации ядра = добавление одного JSON-файла, не переписывание приложения.

## VII. Финальные директивы (фиксация 3)

### 7.1. Парсинг ТУП — искусство разделения
- Парсер — **абсолютный фильтр**, независимо от исходной формы файла (раздельные или слитный монолит).
- Алгоритм **читает структуру листа, находит маркеры дисциплин и сам разделяет их на разные `subject_id`** при заливке.
- Если в одном `.xlsx` встретятся алгебра и геометрия — рассечь на **две независимые сущности `TupDocument`**.
- База получает идеальную чистоту независимо от исходной грязи.

### 7.2. Календарь и даты — отсечение зависимостей
- Внешний `kzCalendarService` и любые API для расчёта дат **запрещены** (принцип Offline-First).
- Производственный календарь Казахстана (каникулы, праздники, переносы) — **локальная таблица SQLite**.
- Учитель скачивает актуальный календарь **один раз на год** (пакет/JSON) → ядро автономно считает все сдвиги по алгоритму адаптивного календарного сдвига (FR-2.4).
- Никаких обращений к сторонним сервисам в момент генерации.

### 7.3. Профиль творца — монолит идентичности
- Таблица **`TeacherProfile`** создаётся немедленно: ФИО, должность, наименование школы, квалификация.
- Вводятся **один раз** при первом запуске.
- Движок материализации (генератор документов) извлекает данные из БД и вшивает их в титульные листы КСП и СОР. Повторный ввод одних и тех же данных запрещён (нормализация).

## VIII. Уточнения заказчика (фиксация 3)

| Решение | Директива |
|---------|-----------|
| Разделение ТУП | **Алгебра и геометрия — разные ТУП**, разделяются и по классу, и по предмету (`subject_id` × `grade`). Парсер обязан отражать это. |
| Поэтапная детализация | Структура и пайплайн уточняются **на каждом этапе реализации**. Текущие решения не финальны для всех слоёв — они фиксируют направление. |
| Даты КТП | Назначение дат — **автоматическое** (по локальному календарю), но **с обязательной возможностью ручного редактирования** каждого урока. |
| Модель школы | Внедряется **целостная модель школы**: директор, завуч, методобъединение и т.д. Все данные хранятся в БД и **автоподставляются в титульные листы** (утверждающие подписи). Не ограничиваться одним профилем учителя. |

## IX. Архитектурные абсолюты модели учреждения (фиксация 4)

### 9.1. Изоляция бюрократии от педагогики
- Модель школы **не смешивается** с нормативным контентом (ТУП).
- ТУП — неизменные законы (педагогика). Школа — преходящая административная оболочка (бюрократия).
- Пересечение — **только в момент генерации документа** (КСП/СОР/СОЧ). В БД контуры существуют параллельно.

### 9.2. Историческая неизменность (Temporal Integrity)
- Должности меняются: завуч уходит, директор сменяется.
- `school_staff` обязана иметь **флаги активности (`is_active`)** и/или **временные метки (`valid_from`, `valid_to`)**.
- Старый КСП, подписанный прошлым директором, при повторном открытии из архива **не переписывается** на новое имя.
- Утверждённый документ — **застывшая история**. Внешние ключи указывают на **конкретную ревизию должности** (snapshot подписей в момент генерации).

### 9.3. Ограничение AcademicStructure
- `AcademicStructure` отражает **физическую реальность школы**: конкретные литеры классов («7 А», «8 Б»), язык обучения, привязку к смене.
- **Не дублировать** абстрактные параллели из ТУП: «7 класс» живёт в ТУП, КСП создаётся для физического «7 А».
- Связь между физическим классом и учебным планом — безжалостно точная (join по `grade` + предмет).

### 9.4. Имплементация в код (монолитные таблицы)

```sql
CREATE TABLE schools (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    region      TEXT,
    created_at  TEXT NOT NULL
);

CREATE TABLE school_staff (
    id        TEXT PRIMARY KEY,
    school_id TEXT NOT NULL REFERENCES schools(id) ON DELETE CASCADE,
    role      TEXT NOT NULL,        -- директор / завуч / председатель МО / ...
    full_name TEXT NOT NULL,
    is_active INTEGER NOT NULL DEFAULT 1,
    valid_from TEXT NULL,
    valid_to   TEXT NULL
);

CREATE TABLE teacher_profiles (
    id        TEXT PRIMARY KEY,
    school_id TEXT NOT NULL REFERENCES schools(id) ON DELETE CASCADE,
    full_name TEXT NOT NULL,
    category  TEXT                  -- педагог-модератор / эксперт / исследователь / ...
);

CREATE TABLE classes (
    id        TEXT PRIMARY KEY,
    school_id TEXT NOT NULL REFERENCES schools(id) ON DELETE CASCADE,
    grade     INTEGER NOT NULL CHECK (grade BETWEEN 1 AND 12),
    letter    TEXT NOT NULL,
    language  TEXT NOT NULL          -- RU / KK
);
```

- Эти таблицы создаются **на этапе нормативного базиса** (вместе с ТУП/КТП), а не позже.

## X. Финальные подтверждения архитектуры (фиксация 5)

### 10.1. Ядро (Rust) — анатомия абсолюта

| Слой | Назначение | Приказ |
|------|------------|--------|
| `commands/` | Тонкий слой интерфейса: приём и выдача | Команды Tauri обязаны возвращать **полностью собранные агрегаты**, готовые к использованию. Фронтенд не собирает осколки DTO. |
| `domain/` | Сердце системы: бизнес-правила и инварианты | `invariants.rs` — отдельный модуль. Законы (45 мин, FR-2.2) вызываются в **Карантинном буфере до** касания репозитория. |
| `db/` | Репозитории — безжалостные исполнители воли домена | Только через асинхронный `sqlx`. |
| `infra/` | Инструменты внешнего мира | OpenCode (stdio), Keyring. |

### 10.2. Фронтенд (React) — дисциплина отражения

| Вопрос | Приказ |
|--------|--------|
| Слой данных | **RTK + thunks** (стойка из KTPHUB). Глобальный стор — не свалка: локальные формы в локальном состоянии, чистота slices. |
| Редактор КТП | **Иерархия `features/`**: Таблица → Строка → Ячейка-редактор. Каждый компонент не знает о других. |
| Дифф-просмотр | **Отдельный полноэкранный `DiffViewer`** — Врата Карантина. Не модалка: учитель видит каждое изменённое слово перед решением. |

### 10.3. Поток данных и контекст

- **Сквозной сценарий генерации КСП подтверждён без разрывов:**
  `React → invoke → сборка 3-Point контекста → OpenCode (stdio) → Quarantine (инварианты) → возврат черновика → DiffViewer (React) → подтверждение → атомарный commit в SQLite`.
- **Любой разрыв цепи — фатальная уязвимость.**

### 10.4. Мульти-пользовательская модель

- Старт — **single-user**: один мастер на ПК.
- Таблицы `School`/`SchoolStaff` — только для титульных листов и подписей.
- Облачные роли откладываются до несокрушимости локального ядра.

## XI. Доктрина Абсолютного Исполнения (фиксация 6)

> Законы поведения кода и агента. Не подлежат обсуждению. Нарушение = крах архитектуры.

### I. Архитектурная чистота и монолитность ядра

| Закон | Директива |
|-------|-----------|
| **Изоляция домена** | Бизнес-логика (инварианты, расчёт 45 минут, валидация баллов СОЧ) **не знает** о существовании БД или UI. Выкована в чистых типах Rust. |
| **Типы как оружие (TDD)** | Искоренены примитивы (`String`, `i32`) для идентификаторов. UUID обёрнуты в **строгие Newtype** (`KspId`, `ObjectiveId`). Ошибка — на этапе компиляции, не исполнения. Компилятор Rust — судья. |
| **Смерть «умному» фронтенду** | React — покорная тень ядра. Не принимает решений, **не считает** интервалы СОР/СОЧ. Передаёт команды (invoke) и отображает агрегаты. Истина — в SQLite и памяти Rust. |

### II. Безжалостное управление ресурсами

| Закон | Директива |
|-------|-----------|
| **Абсолютная асинхронная дисциплина** | Ядро управляется tokio. Главный поток **не блокируется ни на микросекунду**. Диск (sqlx), ожидание OpenCode, file watcher — всё асинхронно. Зависание UI = техническая немощь. |
| **Аскетизм памяти** | RTX 3050 и блок 500 Вт не терпят расточительности. Избегать `.clone()`; ссылки и borrow checker для передачи контекста без выделения памяти. |
| **Контроль локальных процессов** | Дочерние процессы (GGUF, OpenCode CLI) — на коротком поводке. Превышение лимита памяти или таймаута → **безжалостный kill и перезапуск**. Система — повелитель, процессы — расходный материал. |

### III. Бескомпромиссная работа с данными

| Закон | Директива |
|-------|-----------|
| **Офлайн как абсолют** | Сеть = нестабильная иллюзия. Транзакции, генерации, аналитика выполняются так, словно Supabase исчезнет навсегда. |
| **Атомарность транзакций** | Запись из карантина в БД — строгие SQL-транзакции. Сбой на 14-м из 15 дескрипторов → **полный откат**. В БД — либо совершенный документ, либо ничего. |
| **Нетерпимость к галлюцинациям** | Вывод ИИ по умолчанию ошибочен, пока не прошёл **гильотину валидаторов Rust**. JSON-RPC-схемы строго соответствуют структурам данных. Отклонение на символ = отказ. |
